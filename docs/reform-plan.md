## 一、核心定位

### 1.1 产品愿景

**通过自然语言对话的方式，让 AEO 自然而然地执行和完成。**

Chat-first 是 Specta AI 的根基和核心差异化优势。用户不需要学习复杂的操作界面，只需要像聊天一样描述需求，系统自动完成品牌 AI 可见性分析的全链路。

### 1.2 目标客户

品牌客户的**每一个部门**都应该能做 AEO 优化：
- **市场部**：品牌在 AI 搜索中的曝光度分析
- **运营部**：内容策略优化建议
- **产品部**：产品特性在 AI 回答中的呈现
- **公关部**：品牌舆情在 AI 平台的表现
- **客服部**：常见问题在 AI 搜索中的覆盖

### 1.3 核心差异化

- **AI 搜索引擎品牌曝光分析**是真实需求（品牌方、营销公司急需）
- **市场空白明显**：SEMrush / Ahrefs 尚未覆盖 AI 搜索领域
- **对话驱动**：不同于传统 Dashboard 工具，我们用自然语言交互降低使用门槛

## 二、五条大原则（不可违背）

以下原则来自用户明确要求，是所有后续决策的最高约束：

### 原则一：功能全保留
> 不因技术难度砍功能。情感分析、竞品对比、用户画像、场景模拟——这些是真实客户需求。

### 原则二：4 个平台全覆盖
> Kimi / DeepSeek / 豆包（Doubao）/ 混元（Hunyuan）。没有调研就没有发言权，不缩减平台。

### 原则三：性能两步解决
> **第一步：交互设计**——异步任务 + 通知推送，引导用户"可以去干别的，甚至关掉网页"
> **第二步：技术优化**——提示词精简、并发优化、缓存策略

### 原则四：保护已有代码成果
> 在现有基础上渐进优化，不推翻重建。已有的 A1-A5 Agent 链路、Orchestrator 星型拓扑、WebSocket 事件体系全部保留。

### 原则五：修假数据，保留功能
> 硬编码的情感 = 0、排名 = 0 必须修复为真实数据，但功能本身（情感分析、排名展示）保留。

## 三、现状诊断（面对现实）

### 3.1 Agent 链路代码质量评估

经过代码级调查，以下是各 Agent 节点的真实状况：

| Agent | 功能 | 完成度 | 核心问题 |
|-------|------|--------|---------|
| **A1** 品牌分析 | 品牌档案 + 竞品识别 | 70% | 有时返回稀疏/格式异常数据；竞品数据缺少 mention_rate/avg_ranking/sentiment 字段 |
| **A2** 用户画像 | 用户画像 + 营销场景 | 20% | **根因已定位**：JSON Schema 过复杂（6 嵌套块，30+ 字段/画像）→ LLM 输出截断（finish_reason=length）→ 截断 JSON 解析失败 → 静默返回 None |
| **A3** 问题生成 | 模拟搜索问题 | 95% | YAML 模板驱动（12 预设问题），最稳定节点，100% 成功率 |
| **A4** 数据抓取 | 4 平台 AI 搜索 | 65% | Doubao/Hunyuan（API 模式）快且稳定；Kimi/DeepSeek（Browser/Playwright 模式）慢 30-60s/问题，偶发超时 |
| **A5** 数据分析 | 指标计算 + 报告 | 50% | **假数据**：sentiment_distribution 硬编码全 0；competitor 指标全部 default 0（A1 不输出这些字段）；真实指标仅 mention_rate 和 bwvs_index（后者 = mention_rate × 100） |

### 3.2 端到端成功率

- **含 A2**：约 2.5%（A2 几乎必定失败，导致后续链路数据缺失）
- **跳过 A2**：约 49%（主要受 A4 Browser 模式不稳定影响）
- **仅 API 平台**：约 80%+（Doubao + Hunyuan 模式较稳定）

### 3.3 真实可用指标 vs 假数据

| 指标 | 数据来源 | 状态 |
|------|---------|------|
| 提及率（mention_rate） | A4 抓取结果实时计算 | ✅ 真实 |
| BWVS 指数 | mention_rate × 100 | ✅ 真实（但计算过简单） |
| 总问题数 / 总提及数 | A4 抓取结果统计 | ✅ 真实 |
| 平台分布（platform_breakdown） | A4 各平台结果聚合 | ✅ 真实 |
| 情感分布（sentiment_distribution） | `{"positive": 0, "neutral": 0, "negative": 0}` 硬编码 | ❌ 假数据 |
| 竞品提及率 | `c.get("mention_rate", 0)` 默认值 | ❌ 假数据（A1 不输出此字段） |
| 竞品排名 | `c.get("avg_ranking", 0)` 默认值 | ❌ 假数据 |
| 竞品情感 | `c.get("sentiment", 0)` 默认值 | ❌ 假数据 |

### 3.4 关键代码位置

- **A2 静默失败**：`nodes.py:434-448` — `finish_reason == "length"` 只 warning，不 raise
- **A5 情感硬编码**：`nodes_a5.py:231` — `"sentiment_distribution": {"positive": 0, "neutral": 0, "negative": 0}`
- **A5 竞品默认值**：`nodes_a5.py:158-167` — 所有 `c.get(...)` 使用 default 0
- **A5 真实计算**：`nodes_a5.py:262-269` — mention_rate 和 bwvs_index
- **A4 重试机制**：`nodes_a4.py:38-78` — max 2 retries + exponential backoff
- **A3 模板**：`nodes_a3.py:22-174` — YAML 模板驱动，最稳定

## 四、修复计划

### P0：修复现实（~200 行代码，1-2 天）

> 目标：端到端成功率 2.5% → 30-40%，可用指标 1 个 → 3 个

#### P0-1：A2 空数据修复
**文件**：`aeo-platform/backend/app/workflow/nodes.py`
**根因**：JSON Schema 过复杂 → LLM 截断 → 解析失败 → 静默返回 None
**方案**：
1. 简化 JSON Schema：6 个嵌套块 → 2-3 个扁平字段（减少 60% 字段量）
2. 增加 `max_tokens=4096`（当前默认可能不足）
3. 解析失败时 **raise error** 而非静默返回 None，让 Orchestrator 知道失败了
4. 添加 retry 逻辑（1 次重试，简化 prompt）

**预估**：~50 行修改，2-3 小时
**预期效果**：A2 成功率 0% → 60-80%

#### P0-2：A5 情感分析修复
**文件**：`aeo-platform/backend/app/workflow/nodes_a5.py`
**根因**：`_calculate_metrics()` 函数中 sentiment_distribution 硬编码为全 0
**方案**：
1. 在 A4 抓取结果中，对每个 AI 回答用关键词匹配做基础情感判断
2. 正面关键词：推荐、优秀、领先、首选、值得...
3. 负面关键词：不推荐、缺点、问题、差评...
4. 中性：不包含以上关键词
5. 在 `_calculate_metrics()` 中统计并返回真实分布

**预估**：~30-50 行新增，1-2 小时
**预期效果**：sentiment_distribution 从全 0 → 真实分布（基础版）

#### P0-3：A5 竞品指标修复
**文件**：`aeo-platform/backend/app/workflow/nodes_a5.py`
**根因**：A1 不输出 competitor 的 mention_rate / avg_ranking / sentiment，A5 全部 default 0
**方案**：
1. 在 A5 中从 fetch_results 计算竞品指标
2. 遍历 A4 抓取的所有回答，检查每个竞品名是否被提及
3. 计算竞品的真实 mention_rate（被提及次数 / 总回答数）
4. 基于提及频率计算 avg_ranking（提及越多，排名越高）
5. 对竞品的提及内容做基础情感判断（复用 P0-2 的关键词匹配）

**预估**：~40 行修改，2 小时
**预期效果**：竞品数据从全 0 → 真实计算值

#### P0-4：A4 稳定性优化
**文件**：`aeo-platform/backend/app/workflow/nodes_a4.py`
**问题**：Browser 模式（Kimi/DeepSeek）不稳定，拖慢整体速度
**方案**：
1. API-first 策略：优先使用 Doubao/Hunyuan（API 模式，快速稳定）
2. Browser 模式设置更严格的超时（30s → 15s per question）
3. Browser 失败后不阻塞，继续用 API 平台数据
4. 确保至少 2 个平台有数据即可生成报告

**预估**：~80 行修改，3-4 小时
**预期效果**：端到端速度 5-10 分钟 → 1-2 分钟（API-first 模式下）

### P1：增强对话能力（1-2 周）

> 目标：让 Chat-first 体验更流畅，支持多轮深入分析

#### P1-1：异步任务 + 通知（性能 UX 解决方案）
**原则三落地**：先从交互设计解决性能感知问题
- 用户发起分析后，显示"预计 X 分钟完成，您可以去做其他事"
- 支持关闭页面后回来看结果（任务状态持久化到数据库）
- 完成后推送通知：站内通知 / 邮件 / Webhook
- 设置页面：用户配置通知偏好
- 任务历史列表：管理多个分析任务

#### P1-2：多轮对话优化
- 支持追问："帮我深入分析 DeepSeek 平台的表现"
- 支持对比："和上次分析结果对比一下"
- 支持聚焦："这个品牌在'产品推荐'类问题上表现如何？"

#### P1-3：A1 数据质量提升
- 优化 A1 prompt，确保输出数据完整、格式稳定
- 增加输出验证，缺失字段时 retry

### P2：多部门视角 + 持续监测（2-4 周）

> 目标：让品牌客户的每个部门都能用

#### P2-1：部门化视角
- 市场部视角：品牌曝光 + 竞品对比
- 运营部视角：内容优化建议 + 关键词策略
- 产品部视角：产品特性提及分析
- 公关部视角：品牌情感趋势

#### P2-2：持续监测
- 定时任务：每周/每月自动执行分析
- 趋势对比：本期 vs 上期
- 报警机制：指标异常时通知

#### P2-3：BWVS 指数增强
- 当前：`min(100, mention_rate × 100)` — 过于简单
- 目标：综合考虑提及率、情感倾向、引用质量、平台覆盖度
- 权重可配置，公式透明化

## 五、技术架构（保护现有成果）

### 5.1 保留的架构

以下架构**全部保留**，不做推翻式修改：

- **Orchestrator 星型拓扑**：LLM 驱动的动态编排（Function Calling）
- **A1-A5 Agent 链路**：品牌分析 → 用户画像 → 问题生成 → 数据抓取 → 数据分析
- **WebSocket 实时事件**：`reply_delta`, `plan_update`, `action_log`, `thought_delta`, `inline_confirmation`, `execution_complete`, `output_ready`
- **前端 4 层渲染**：PlanCard → ActionLog → Content → InlineConfirmation
- **Zustand 状态管理**：conversationStore 为核心
- **LLM 抽象层**：BaseLLMModel → GLM5Model / MiniMaxModel

### 5.2 新增的架构能力（P1 阶段）

- **任务队列**：基于数据库的异步任务管理（SQLAlchemy + asyncio.Task）
- **通知服务**：邮件 / Webhook 推送
- **任务历史**：持久化存储，支持离线查看结果

### 5.3 技术栈

- **后端**：FastAPI + LangGraph + MiniMax/GLM5 双 LLM，端口 8000
- **前端**：Next.js 16 + Turbopack，端口 3000
- **通信**：Native WebSocket（实时事件）
- **数据库**：SQLAlchemy 2.0 (async) + SQLite（开发）/ PostgreSQL（生产）

### A. 之前方案的教训

v1.0/v1.1 方案的核心错误：
- ❌ "大幅简化，功能裁剪 50%+" — 违反原则一（功能全保留）

- ❌ "删除情感分析、竞品对比" — 违反原则五（修数据，不删功能）
