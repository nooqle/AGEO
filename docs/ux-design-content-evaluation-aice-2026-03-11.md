# AI 采信评估交互细化文档

> **设计师**: Don Norman
> **日期**: 2026-03-11
> **状态**: 交互细化稿
> **前置文档**: `docs/design-content-evaluation-aice-2026-03-10.md`, `docs/prd-content-evaluation-aice-2026-03-11.md`

---

## 1. 设计目标

本文件聚焦“AI 采信评估”能力在现有 Specta AI 平台内的具体交互落地，回答以下问题：

1. 用户从哪里发起单条和批量评估
2. 用户在执行过程中看到哪些反馈
3. 报告如何嵌入现有 Chat + Canvas + Artifact 结构
4. 批量任务如何避免认知混乱
5. 现有组件哪些复用，哪些需要新增

本设计默认遵循现有平台约束：

1. 不新增一级页面
2. 不打破 Chat-first 主流程
3. 不新增平行报告体系
4. 批量能力必须在当前工作台内自然扩展

---

## 2. 核心设计原则

| 原则 | 说明 |
| :--- | :--- |
| Chat-first | 所有发起、确认、补充输入、失败重试都以 Chat 为主入口 |
| Artifact-first | 正式结果进入 Canvas，聊天正文只放摘要与引导 |
| Recognition over recall | 用户始终知道“当前评估的是哪条内容、哪一批内容” |
| Progressive disclosure | 先看总分和结论，再看维度明细，再看证据与修改建议 |
| Batch without overload | 批量任务必须拆成总览、明细、详情三层，不能塞成一页 |
| Safe failure | 单项失败不能让整批任务失去可用性 |

---

## 3. 信息架构

### 3.1 单条评估

```text
Chat 发起
  ->
执行中反馈
  ->
Chat 摘要结论
  ->
Canvas: 内容评估报告
```

### 3.2 批量评估

```text
Chat 发起
  ->
执行中反馈（批次级 + 单项级）
  ->
Chat 摘要结论
  ->
Canvas:
     1. 批量总览报告
     2. 批量评分明细表
     3. 单项详情报告（按需打开）
```

### 3.3 Canvas 交付物层次

| 层级 | Artifact 类型 | 用途 |
| :--- | :--- | :--- |
| 一级 | `report` | 单条评估报告 / 批量总览报告 |
| 一级 | `dataTable` | 批量评分明细表 |
| 二级 | `report` | 某一条的单项详情报告 |

## 4. 入口设计

## 4.1 入口 A：抓取结果里的引用操作

### 交互目标

让用户在看到 A4 抓取结果时，直接对某条 citation 发起评估，而不需要复制 URL 再回到输入框手动描述。

### 位置

在 `FetchResultsContent` 的每条 citation 卡片或行项目右侧增加轻量操作按钮：

1. `评估此引用`
2. Phase 2 增加 `加入批量评估`

### 单条交互流程

```text
用户浏览引用
  ->
点击“评估此引用”
  ->
Chat 自动插入一条用户消息
  ->
系统执行单条评估
```

### 推荐消息文案

```text
请评估这条引用来源是否容易被 AI 采信，并给出修改建议。
来源：https://example.com/article
```

### 设计理由

1. 避免用户自己组织描述语句
2. 让动作显得是“对当前结果的进一步分析”
3. 保持和现有抓取结果页的上下文连续性

## 4.2 入口 B：Chat 直接输入 URL

用户直接粘贴：

```text
帮我评估这个网页：https://example.com/article
```

### 系统响应

系统识别到 URL 后，不应立即给长说明，而是先返回一条简短对象确认消息：

```text
将评估 1 个网页来源：
- 域名：example.com
- 模式：AICE-Web
```

然后进入执行。

## 4.3 入口 C：Chat 直接输入文本

用户直接粘贴文案并要求评估。

### 系统响应

应在 Chat 中先回显：

```text
将评估您输入的文本内容：
- 内容类型：用户文本
- 长度：约 860 字
- 模式：AICE-Text
```

重点是帮助用户确认系统理解正确，而不是强制二次确认。

## 4.4 入口 D：Chat 批量输入

### 批量 URL

```text
请批量评估下面这些网页：
https://a.com/1
https://b.com/2
https://c.com/3
```

### 批量文本

```text
请批量评估以下 3 段文案：
===ITEM===
文案 1
===ITEM===
文案 2
===ITEM===
文案 3
```

### 系统响应

系统不应直接开始跑，而应先输出批次摘要：

```text
已识别到 3 个评估对象：
- 3 个网页
- 执行模式：批量网页评估
- 结果将以“总览报告 + 明细表”方式交付
```

或：

```text
已识别到 5 段文本：
- 执行模式：批量文本评估
- 结果将以“总览报告 + 明细表”方式交付
```

## 5. 单条评估交互细化

## 5.1 执行前状态

### Chat 中显示

1. 评估对象说明
2. 评估模式（AICE-Web / AICE-Text）
3. 预计输出内容说明：总分、风险、修改建议

### 不建议显示的内容

1. 太多技术细节
2. 大段评分规则全文
3. 复杂确认按钮

MVP 只需要让用户知道系统评估的是哪条内容即可。

## 5.2 执行中状态

建议使用现有 Action Log 和 TaskStatusBadge 表达过程，不新增复杂进度组件。

### 推荐阶段文案

| 阶段 | 文案 |
| :--- | :--- |
| `source_parse` | 正在识别输入内容 |
| `content_extract` | 正在抽取正文与结构信息 |
| `aice_score` | 正在按 AICE 维度评分 |
| `report_generate` | 正在生成评估报告 |

### Chat 内表现

1. 顶部轻量 badge 持续显示“评估中”
2. Action log 逐条流出
3. 不建议在消息正文持续输出大段中间结果

## 5.3 完成状态

完成后 Chat 中只放摘要：

```text
评估完成。
该内容 AI 采信友好度为 76 分，主要问题集中在结构化标记和可核查性不足。
完整报告已在右侧打开。
```

### Canvas 自动打开

自动打开该条的评估报告 Tab。

## 6. 单条评估报告设计

## 6.1 顶部摘要区

应包含：

1. 报告标题：`内容评估报告`
2. 来源标题或文本摘要
3. 评分模式
4. 总分
5. 分数档位
6. 一句话结论

### 示例

```text
内容评估报告
example.com / AICE-Web
AI 采信友好度：76 / 100
结论：基础可信度较好，但结构化与可核查性不足，仍会限制 AI 采信稳定性。
```

## 6.2 报告分区顺序

推荐固定顺序：

1. 总分摘要
2. 算式验证区块
3. 维度得分表
4. 容易被 AI 采信的原因
5. 需审慎对待的原因
6. 修改建议
7. 证据锚点

这个顺序符合用户认知：

- 先知道好坏
- 再知道为什么
- 最后知道怎么改

## 6.3 修改建议区的交互要求

修改建议必须是**可直接执行**的。

每条建议至少包含：

1. 对应维度
2. 问题说明
3. 操作指令
4. 示例文案或代码
5. 修改目的

### 不合格写法

```text
建议增强内容可信度。
```

### 合格写法

```text
针对 C3 可核查性：
在段落末尾补充 1-2 个官方来源链接，并明确数据出处。
示例：将“公司增长迅速”改为“根据 2025 年年度报告，公司营收同比增长 18%”。
```

## 7. 批量评估交互细化

## 7.1 为什么批量不能沿用单条模式

如果一次评估 20 条内容，还按单条模式一条条弹报告，会导致：

1. Chat 被大量重复完成消息刷屏
2. Canvas 一次打开太多 Tab
3. 用户无法先看整体优先级

因此批量必须引入“批次”心智。

## 7.2 批量任务开始状态

### Chat 应显示批次摘要

```text
已开始批量评估：
- 批次对象：12 个网页
- 执行模式：批量网页评估
- 输出结果：总览报告 + 评分明细表
```

### 如为批量文本

```text
已开始批量评估：
- 批次对象：8 段文本
- 执行模式：批量文本评估
- 输出结果：总览报告 + 评分明细表
```

## 7.3 执行中状态

批量任务要同时表达两个层次：

1. **批次级进度**：当前已完成多少项
2. **单项级状态**：成功、失败、重试中

### 推荐表现方式

#### 方案 A：Chat 主消息 + Action Log

主消息：

```text
正在批量评估 12 个网页，目前已完成 7/12。
```

Action log：

```text
item_001 抽取完成
item_002 评分完成
item_003 抽取失败，已标记为失败
item_004 进入重试
```

这是 MVP 最推荐方案，因为复用成本最低。

## 7.4 批量完成状态

Chat 中只输出批次摘要，不逐条刷屏：

```text
批量评估完成。
- 总数：12
- 成功：9
- 失败：3
- 平均分：64
- 最需要优先处理的问题集中在 C9a、C9b、C3
完整结果已在右侧打开。
```

## 8. 批量结果设计

## 8.1 批量总览报告

这是给“管理视角”看的。

### 目标

让用户快速知道：

1. 这一批整体质量如何
2. 哪些问题最普遍
3. 哪些项最该优先处理

### 页面结构

1. 批次摘要卡
2. 核心指标卡
3. 低分维度分布
4. Top 风险项列表
5. 批量优化建议摘要

### 核心指标卡建议

1. 平均分
2. 中位分
3. 低于 60 分的数量
4. 高风险项数量
5. 失败项数量

## 8.2 批量评分明细表

这是给“执行视角”看的。

### 目标

让用户按条操作。

### 表格列建议

1. `序号`
2. `类型`
3. `标题 / 文本摘要`
4. `总分`
5. `档位`
6. `最高风险维度`
7. `状态`
8. `操作`

### 操作列

支持：

1. `查看详情`
2. `重试`（失败项）
3. Phase 2 支持 `加入优化任务`

## 8.3 单项详情打开方式

点击 `查看详情` 后：

1. 若该单项详情报告已生成，则直接切换到对应 Tab
2. 若未生成，则延迟生成并打开

### 推荐策略

对低分项自动生成详情报告，对中高分项按需生成。

原因：

1. 控制批量任务总体耗时
2. 控制 Canvas Tab 数量
3. 让资源集中在最需要处理的项上

## 9. 失败与异常交互

## 9.1 单条评估失败

单条失败时，Chat 中应明确失败原因，而不是只显示“任务失败”。

### 推荐文案

```text
评估未完成。
原因：该页面无法稳定抽取正文，已降级为可访问性风险。
您可以稍后重试，或直接粘贴页面文本内容进行评估。
```

### CTA

1. `重试评估`
2. `改为评估文本`

## 9.2 批量评估部分失败

批量任务中最重要的是让用户理解：**整批已完成，但其中部分失败。**

### 推荐摘要

```text
批量评估已完成（部分成功）。
- 成功：9
- 失败：3
失败项已在明细表中标记，可单独重试。
```

### 表格中的失败态

每个失败项显示：

1. 状态：`failed`
2. 失败原因简述
3. 操作：`重试`

## 9.3 无内容可评估

例如用户输入的是空文本、无效 URL、或无法识别的混合输入。

### 推荐文案

```text
未识别到可评估内容。
请提供：
- 单个网页 URL
- 一段文本
- 或多条 URL / 多段文本用于批量评估
```

## 10. 组件复用与新增建议

## 10.1 建议复用的现有组件

| 组件 | 用途 |
| :--- | :--- |
| `ChatPanel` | 发起与展示摘要 |
| `TaskStatusBadge` | 批次级状态 |
| `OutputCard` | 单条报告、批量总览、明细表入口 |
| `CanvasPanel` | 报告承载 |
| `ReportContent` 外层容器 | 统一报告皮肤 |
| `DataTableContent` | 承载批量评分明细 |
| `ArtifactNav` | 多交付物切换 |

## 10.2 建议新增组件

| 组件 | 是否必须 | 用途 |
| :--- | :--- | :--- |
| `EvaluationReportContent` | 必须 | 渲染单条评估报告正文 |
| `BatchEvaluationReportContent` | 建议 | 渲染批量总览报告 |
| `BatchEvaluationTableAdapter` | 建议 | 将批量结果映射到 `dataTable` |
| `CitationEvaluateAction` | 建议 | 抓取结果中“评估此引用”按钮封装 |

## 10.3 不建议新增的组件

1. 独立的“内容评估页面”
2. 独立的“批量任务中心页面”
3. 独立的“评估结果弹窗系统”

理由很简单：都会打破现有主工作流。

## 11. 批量与单条的一致性要求

必须保持以下一致性：

1. 单条与批量的评分维度定义一致
2. 报告中“总分 -> 原因 -> 建议”的顺序一致
3. 所有结果都能通过 ArtifactNav 找到
4. 所有结果都可以回到对应对话消息
5. 单项详情报告视觉上与单条报告完全一致

这样用户学会一次，就能在两种模式下复用心智。

## 12. 验收标准（UX 视角）

### 单条评估

- [ ] 用户可以从引用卡片直接触发评估
- [ ] 用户输入 URL 或文本时，系统能正确回显评估对象说明
- [ ] 执行中能看到清晰进度反馈
- [ ] 完成后 Chat 只显示摘要，完整结果进入 Canvas
- [ ] 报告结构清晰，修改建议可执行

### 批量文本评估

- [ ] 用户一次输入多段文本时，系统能正确识别为批量任务
- [ ] Chat 能显示批次级摘要和执行反馈
- [ ] Canvas 产出总览报告和明细表
- [ ] 用户能从明细表进入单项详情

### 批量网页评估

- [ ] 用户一次输入多条 URL 时，系统能正确识别为批量网页评估
- [ ] 任务执行过程中不会刷屏式输出单条完成消息
- [ ] 部分失败时，用户仍能拿到完整的成功项结果
- [ ] 失败项在明细表中可被识别并重试

---

## 13. 最终建议

最推荐的落地顺序是：

1. 先做单条评估交互
2. 再做批量文本交互
3. 最后做批量网页交互

原因：

1. 单条评估先验证报告结构是否好用
2. 批量文本先验证批次交互是否清楚
3. 批量网页最后接入高不确定性的抓取能力

这是用户认知成本最低、工程风险最可控的路线。
