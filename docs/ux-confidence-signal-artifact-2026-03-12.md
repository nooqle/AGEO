---

## 1. 设计目标

`置信度信号` 不是一张静态报告，而是一个围绕 A4 citation 结果展开的可交互交付物。

它要同时满足 3 个目标：

1. 让用户快速判断 A4 引用来源是否可靠、是否容易被 AI 采信
2. 让用户在同一个上下文容器里继续追加评估
3. 避免把这类评估动作再次推回全局 Chat 输入框

---

## 2. 用户心智

用户在这个交付物中的心智应当是：

```text
这些是 A4 回答里引用到的来源
  ->
系统已经替我做了基础置信度判断
  ->
我可以继续补充链接或文本做额外评估
  ->
所有结果都留在同一个工作面板里
```

这和 Chat 的心智不同。

Chat 的心智是“我在和 Agent 对话”。  
`置信度信号` 的心智是“我在查看并扩展一个评估工作面板”。

---

## 3. 交付物定位

建议对外名称：

- 中文：`置信度信号`
- 英文内部名：`Confidence Signal`

建议承载方式：

- 一级类型继续复用 `report`
- `report_kind = confidence_signal`

理由：

1. 不破坏当前 Canvas 结构
2. 可复用现有 Header、Tab、版本历史
3. 允许在 `ReportContent` 下分支出专用渲染器

---

## 4. 主流程

```text
A4 抓取完成
  ->
系统提取所有 citation URL
  ->
A7 对 citation 批量执行 AICE-Web
  ->
Canvas 自动出现“置信度信号”交付物
  ->
用户查看自动评估结果
  ->
用户在“额外评估”输入框中粘贴 URL 或文本
  ->
主 LLM 在 artifact 上下文中判断输入类型并驱动 A7
  ->
结果增量更新到同一个交付物
```

---

## 5. 信息架构

推荐将交付物拆成 5 个区块：

1. 顶部摘要区
2. citation 置信度列表
3. 风险聚合与建议
4. `额外评估` 输入区
5. 手动追加结果区

### 5.1 顶部摘要区

内容：

- 交付物标题：`置信度信号`
- 副标题：例如 `已评估 18 个引用来源`
- 全局摘要指标
  - 高置信来源数
  - 中风险来源数
  - 低可信来源数
  - 平均 AICE 分
- 最新更新时间

这一区域要回答一个问题：

**“这一批引用来源整体上靠不靠谱？”**

### 5.2 citation 置信度列表

每条 citation 作为一个独立卡片或列表行，展示：

- 标题
- 域名
- 是否官网 / 官方
- AICE 总分
- 信号等级
  - `高置信`
  - `中性`
  - `需审慎`
- 2-3 个维度摘要标签
  - `Coverage 0`
  - `缺少 Schema`
  - `时效性风险`
- `查看详细评估`

推荐默认只展开摘要，不直接把 9C 明细全铺开。

### 5.3 风险聚合与建议

这个区块用于汇总 citation 的共性问题，例如：

- 多数链接缺少 Schema
- 多数链接来自低权威商业站点
- 日期缺失严重
- 引用集中在少数域名

这一区块要回答：

**“这批引用为什么整体可信或不可信？”**

### 5.4 `额外评估` 输入区

这是本方案的关键交互。

推荐形式：

- 固定在交付物中下部
- 一个明显的输入容器
- 风格参考 NotebookLM 的 source 输入，但更紧凑

输入区结构：

1. 标题：`额外评估`
2. 提示文案：`粘贴一个链接或一段文本，继续做 AICE 评估`
3. 多行输入框
4. 辅助说明：
   - `支持 URL`
   - `支持文本`
   - `暂不支持问题抓取`
5. 主按钮：`开始评估`

### 5.5 手动追加结果区

这个区块专门展示用户通过 `额外评估` 加进来的结果。

需要显式区分来源：

- `自动引用评估`
- `手动追加评估`

这样用户不会把 A4 的 citation 和自己追加的内容混在一起。

---

## 6. `额外评估` 的交互原则

### 6.1 不是迷你 Chat

这个输入框不能设计成一个小型对话系统。

用户在这里的任务非常单一：

1. 粘贴 URL
2. 或粘贴文本
3. 触发评估

不要允许在这里输入：

- “帮我顺便抓取这几个问题”
- “重新跑 A4”
- “比较竞品”

否则会重新把复杂度带回来。

### 6.2 输入限制要明确可见

输入框 placeholder 建议直接写清：

```text
粘贴链接或文本，生成额外评估
```

按钮下方辅助文案建议写：

```text
支持单个链接、多个链接、或一段文本；不支持问题抓取命令
```

### 6.3 即时反馈

提交后必须立即给出局部反馈：

- `正在评估 1 个链接`
- `正在评估 3 个链接`
- `正在评估 1 段文本`

不能让用户怀疑“点了有没有反应”。

## 7. 状态设计

### 7.1 初始加载态

当 citation 自动评估还在进行中：

- 顶部摘要区显示 skeleton
- citation 列表逐项出现
- 每项显示 `评估中`

### 7.2 部分完成态

如果 citation 批量评估正在分批返回：

- 已完成项显示分数和标签
- 未完成项显示 loading
- 顶部摘要区展示：
  - `已完成 8 / 18`

### 7.3 空态

如果当前 A4 结果没有 citation：

- 显示空态说明
- 仍保留 `额外评估` 输入区

文案建议：

```text
当前回答未检测到可评估的引用来源。
你仍可粘贴链接或文本，手动生成置信度信号。
```

### 7.4 错误态

区分两类错误：

1. 系统级错误
   - `本次 citation 评估失败，请重试`
2. 单项错误
   - `该页面无法稳定读取`

单项错误不能拖垮整个交付物。

### 7.5 增量更新态

用户执行 `额外评估` 后：

- 输入区显示 loading
- 当前交付物不跳走
- 新结果插入 `手动追加评估` 区
- 顶部摘要同步更新

---

## 8. 列表与明细切换

### 8.1 默认只看摘要

每条 citation 默认展示：

- 标题
- 域名
- AICE 总分
- 信号等级
- 3 个关键标签

### 8.2 点击后展开明细

点击 `查看详细评估` 后，在当前交付物内展开：

- 9C 维度分数
- 关键证据
- 风险原因
- 修改建议

不建议一上来为每个 citation 单独开新的 Canvas Tab。

### 8.3 何时开新报告

只有两种情况建议生成额外 artifact：

1. 用户明确点击 `在独立报告中打开`
2. 某条 `额外评估` 需要深度查看和复制

默认交互仍应留在 `置信度信号` 面板内部。

---

## 9. 视觉与组件建议

### 9.1 列表层级

建议按风险等级分组：

1. `需优先关注`
2. `中性来源`
3. `高置信来源`

这比单纯按时间或域名排序更有行动价值。

### 9.2 信号标识

建议使用统一的信号标签系统：

- 绿色：`高置信`
- 琥珀：`中性`
- 红色：`需审慎`

不要把视觉重点全放在 numeric score 上，用户更容易先看标签再看分数。

### 9.3 输入区风格

输入区要和正文区明显区隔，但不要像 Chat 输入栏那样占据整个底部。

建议做成：

- 柔和背景容器
- 明显边框
- 标题 + 说明 + 输入框 + CTA

这样用户会理解它是“工作面板内的追加动作”，不是全局对话入口。

## 10. 用户文案建议

### 10.1 顶部说明

```text
系统已对本轮回答中的引用来源进行 AICE 评估，帮助判断这些来源是否稳定、可信、易被 AI 采信。
```

### 10.2 `额外评估` 区

标题：

```text
额外评估
```

说明：

```text
粘贴一个链接或一段文本，继续生成置信度信号。
```

Placeholder：

```text
输入链接或文本…
```

辅助说明：

```text
支持链接和文本，不支持问题抓取命令
```

## 11. UX 验收标准

### 11.1 可理解性

首次使用的用户应能在不看帮助的情况下理解：

1. 这个交付物是在分析 citation 来源
2. 哪些结果是系统自动生成的
3. 哪些结果是我后来手动追加的
4. 我可以在这里继续贴链接或文本做额外评估

### 11.2 可控性

用户在提交 `额外评估` 后，应始终知道：

1. 系统正在处理什么
2. 当前处理进度
3. 新结果会出现在哪里
4. 出错时如何恢复

### 11.3 一致性

整个体验必须保持：

1. 仍然是现有 Canvas Artifact 的一部分
2. 不像额外长出一个新产品
3. 不要求用户切换到独立页面

---

## 12. UX 结论

`置信度信号` 交付物的价值不在于“把评估结果塞进一个新 tab”，而在于：

1. 它让 citation 评估天然附着在 A4 结果之后
2. 它给用户一个明确、受限、可持续追加的工作面板
3. 它把原本混乱的 Chat 任务切换，变成一个上下文清楚的局部动作

只要 `额外评估` 不是被做成迷你 Chat，而是被做成明确的局部输入动作，这个方案的可用性会显著高于之前的 Chat-first 路径。
