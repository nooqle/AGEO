## 0.0 E1–E4 和「蓝图约 50%」是什么关系？

这是**两套尺子**，不要混成一个百分比。

```
┌─────────────────────────────────────────────────────────────┐
│  蓝图整本完成度 ≈ 45–55%（战略 + 平台化 + 复利闭环 + Orch…）  │
│                                                             │
│   ┌─────────────────────────────────────────────────────┐   │
│   │  演进主路径 3a→3c 能力竖切 ≈ 75–80%                  │   │
│   │  （Wave A–D 做的就是把这条竖切打通并补强）            │   │
│   └─────────────────────────────────────────────────────┘   │
│                                                             │
│   ┌─────────────────────────────────────────────────────┐   │
│   │  完善轨 E1–E4  ← 不新增蓝图大功能                     │   │
│   │  目标：把「能跑的竖切」做成「可托付的工作台」          │   │
│   │  拉动的是「质感/可维护/旅程」完成感，不是 3c 功能数   │   │
│   └─────────────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────────────┘
```

| 尺子 | 量的是什么 | A–D 后 | E 轨做完后（估） |
|---|---|---|---|
| **整本蓝图 ~50%** | 终局愿景：Chat 生成整图、校准闭环、Orch 巨石实现、平台化、自创节点… | ~50% | **仍约 55%**（功能边界几乎不变） |
| **3a–3c 能力竖切** | 图可约束/可改/可记/可跑/Chat 能改图 | ~78% | **仍约 78–80%**（不靠 E 加功能） |
| **可交付完成感 / 非半吊子** | 用户是否看得懂、工程师是否敢改、演示是否稳 | **偏低（半吊子感）** | **目标明显抬升（成稿感）** |

**E1–E4 各自对应哪条「成稿命题」：**

| 子波 | 命题 | 对 50% 的影响 |
|---|---|---|
| **E1** 旅程文案 | 用户旅程简洁清晰 | **不提高**蓝图功能 %；提高「用得懂」 |
| **E2** 视觉 Dialog/加载 | 视觉交互统一提质感 | 同上 |
| **E3** 缓存/首屏重试 | 代码优化与稳健 | 同上；降低冷启动翻车 |
| **E4** Chat 编排逻辑外提 | 代码简化拆分（第一刀） | 为以后 Orch/功能波降低成本；**不是** Orch 7k 拆完 |

**一句话：**  
A–D = **把蓝图主竖切做出来**（抬高 3a–3c %）。  
E1–E4 = **把已做出来的东西磨到能托付**（抬高「非半吊子」完成感；整本蓝图仍约一半，因为终局大块还没做）。

## 0. 为什么现在必须「先完善」

A–D 把能力竖切打通了：**图可约束、可改、可记、可荐、Chat 可改图、按图可跑**。  
但若不同时收口下面三条，系统仍是「能演示的半吊子工程」：

| 命题 | 半吊子表现 | 成稿表现 |
|---|---|---|
| **视觉交互** | 生产线/Chat/编排卡各自一套灰条、偶发旧 AI 语汇、原生 confirm | 统一 Specta 纸面+Teal；同一交互语法 |
| **代码/缓存** | God 文件、重复请求、冷启动 Failed to fetch、prompt 前缀不稳 | 边界清晰、可测、可缓存、改一处不炸全身 |
| **用户旅程** | 双入口心智（Chat vs 生产线）、步骤多、术语叠床架屋 | 一条主叙事：定干法 → 改/记 → 跑 → 看证据 |

**纪律：** 完善轨期间，**默认不开**新蓝图大功能（节点 annotation 全量、Orch 自由模式生成整图、自创代码节点、平台化第二垂直），除非完善项明确依赖。

## 1. 三条必达命题（验收语言）

### P1 — 视觉交互：调整 · 统一 · 优化 · 提质感

**原则来源：** `.impeccable.md`、`docs/design-global-visual-principles-2026-04-26.md`、Chat/Canvas/Dashboard 细则。

| 目标 | 完成定义（可勾选） |
|---|---|
| P1.1 色与角色统一 | 生产线/编排/Chat 编排卡：主行动=Teal；中性=纸面；错误=红；**无** indigo/violet/cyan 装饰主调 |
| P1.2 组件语法统一 | 卡片圆角/边框/标题层级/按钮高度同一套；危险确认优先站内 Dialog（覆盖配方等） |
| P1.3 密度与呼吸 | 编排区不再「工具条堆叠感」；分组标题清晰；空态是产品时刻不是空白 |
| P1.4 跨面一致 | Console flow、Chat 预览卡、配方建议条 **同一信息架构**（标题 → 摘要 → 理由 → 主/次行动） |
| P1.5 扫描护栏 | 变更面 `???`=0；旧 AI 调性词扫描过关 |

**非目标：** 整站 rebrand、暗色主题、营销页重做。

---

### P2 — 代码：优化 · 简化 · 拆分 · 缓存命中

| 目标 | 完成定义 |
|---|---|
| P2.1 边界不回潮 | Canvas 壳 **&lt; 1600**；ChatPanel **不**再塞编排业务（只接线）；新逻辑进 lib/组件/service |
| P2.2 高价值拆分 | 按 `god-file-split-backlog`：**优先**与旅程相关的 FE 巨石减负 + Orch **按设计稿做第一刀可运行拆分**（可分期，禁止与视觉大改混成不可审 PR） |
| P2.3 请求与状态缓存 | 拓扑/配方/events/推荐：避免「同 entity 连打 N 次」；失败可重试；首进 Console 冷失败有降级文案 |
| P2.4 Prompt / 编译 cache 友好 | 稳定前缀文件少改；易变 digest 放 user 尾；拆分不破坏 `topology_ops_compiler` 前缀稳定性 |
| P2.5 可测 | 关键纯函数有测；拆分后 3b1/相关套件不红 |

**非目标：** 一次拆完 7k orchestrator + 6k a5 + DashboardViews；禁止「为拆而拆」无验收。

---

### P3 — 用户旅程：简洁 · 清晰 · 不复杂

**主叙事（唯一）：**

```
选品牌 → 看/定生产线（图）→ （可选）改图或套配方 → 运行 → 看证据 → （可选）存/覆盖配方
```

| 目标 | 完成定义 |
|---|---|
| P3.1 主路径步数可数 | 新手从进 Console 到「看懂要跑什么」**≤ 3 个决策点**（选品牌 / 是否改干法 / 运行） |
| P3.2 双入口不打架 | Chat 改图与生产线改图 **结果同一权威拓扑**；文案统一「生产线 / 配方 / 应用变更」 |
| P3.3 术语收敛 | 对外固定：生产线、配方、编排变更、运行；少暴露 ops/topology/version 除非错误态需要 |
| P3.4 失败可理解 | 409/无 entity/冷启动：一句人话 + 一个下一步（刷新 / 去生产线 / 重试） |
| P3.5 无多余闸 | 不恢复「运行二道闸」；改图仍需确认；不自动套用/开跑 |

**非目标：** 砍掉 Chat 主分析能力；重做整个 Dashboard 信息架构。

## 4. 与蓝图完成度的关系（复审口径）

| 口径 | A–D 后 | 完善轨目标后再估 |
|---|---|---|
| 3a–3c 能力竖切 | ~75–80% | 能力数不变，**可交付完成度感**升到 ~85%+ |
| 产品命题（含质感/旅程） | ~65% | **目标 ≥80%**（半吊子线） |
| 整本蓝图（含 Orch 实现/复利闭环） | ~50% | 完善后仍 ~55–60%；其余靠后续功能波 |

**完成定义（产品）：** 演示路径不靠讲解员补课；工程师改编排不踩 God 文件；用户不问「我现在该点哪」。
