## 1. 问题陈述

当前 Specta AI 已经能够完成品牌分析、问题生成、答案抓取和报告输出，但仍缺少一个关键闭环：

用户看到 AI 回答中的引用来源后，无法在平台内直接判断：

1. 这些引用页面为什么会被 AI 采信
2. 自己的网页或文案为什么不容易被 AI 采信
3. 应该如何具体修改网页或文本，提升被 AI 模型引用和采信的概率

这导致平台当前更多停留在“发现问题”，而没有进一步进入“评估内容资产质量并指导修改”的环节。

因此需要新增一条产品能力线：**AI 采信评估（Content Evaluation / AICE Evaluation）**。

---

## 2. 产品目标

### 2.1 目标

1. 让用户可以在 Specta AI 内直接评估网页或文本的 AI 采信友好度
2. 让用户理解页面/文本被扣分的原因，而不是只看到一个总分
3. 让用户获得可执行的修改建议，可直接用于改页面或改文案
4. 与现有 Chat + Canvas + Artifact 体系自然融合，不增加新的主页面
5. 支持从单条评估平滑扩展到批量评估

### 2.2 非目标

当前版本不追求：

1. 做成全功能 SEO 站点审计工具
2. 做成自动改稿器
3. 在 Dashboard 直接做资产全量运营看板
4. 在 MVP 阶段支持复杂文件导入与大规模站点爬取

---

## 3. 目标用户

### 3.1 核心用户

1. 品牌分析师
2. 内容运营 / SEO / AEO 负责人
3. 市场团队内容编辑
4. 需要优化官网、文章页、品牌介绍页的客户侧用户

### 3.2 用户核心任务

1. 评估某个引用链接是否值得信
2. 评估自己某个网页是否容易被 AI 采信
3. 评估自己的一段品牌文案是否太宣传化、不可核查、结构不清晰
4. 在多个网页/多个文本中找出最差项和优先修改项

## 4. 功能范围

## 4.1 Phase 1：单条评估 MVP

### In Scope

1. 评估单条引用链接
2. 评估用户输入的单个网页 URL
3. 评估用户输入的单段文本
4. 输出单条评估报告
5. 输出可执行修改建议
6. 支持版本历史

### Out of Scope

1. 批量网页评估
2. 批量文本评估
3. 文件导入
4. 自动改写正文

## 4.2 Phase 1.5：批量文本 MVP

### In Scope

1. 一次输入多段文本
2. 生成批量总览报告
3. 生成批量评分明细表
4. 支持从明细表查看单项详情

### Out of Scope

1. 批量网页抓取
2. 上传 csv/txt/json
3. 单项失败重跑复杂调度

## 4.3 Phase 2：批量网页增强版

### In Scope

1. 一次输入多条 URL
2. 生成批量总览报告 + 明细表
3. URL 抓取并发控制
4. 单项失败标记与重试
5. 部分成功任务交付

### Out of Scope

1. 大站级批量爬取
2. 跨域权限受限页面抓取
3. 文件导入批量任务

## 4.4 Phase 3：文件导入与闭环优化

1. 上传 csv/txt/json 批量导入
2. 一键复制修改建议
3. 从评估报告生成优化后版本
4. 评估结果回写优化任务队列
5. Dashboard 资产健康度视图

## 5. 用户故事

### US-1：评估单个引用链接

作为品牌分析师，我希望在查看抓取结果时，能直接评估某条引用链接的 AI 采信友好度，从而判断这个来源是否值得作为参考对象。

**验收标准**：
- 抓取结果中的 citation 支持点击“评估此引用”
- 点击后在当前 Chat 会话内启动评估
- Canvas 产出单独的内容评估报告
- 报告包含总分、维度得分、风险原因、修改建议

### US-2：评估自己的网页

作为内容负责人，我希望输入一个网页 URL，就能知道该页面为什么容易或不容易被 AI 采信。

**验收标准**：
- 用户在 Chat 中输入 URL
- 系统识别为网页评估请求
- 报告使用 AICE-Web 模式
- 报告中包含结构、时效、可信度、可核查性等维度评分

### US-3：评估自己的文本文案

作为市场编辑，我希望粘贴一段文案，系统能告诉我这段文本在 AI 采信角度上的问题，并给出修改建议。

**验收标准**：
- 用户粘贴文本并要求评估
- 系统识别为文本评估请求
- 报告使用 AICE-Text 模式
- 报告明确哪些问题来自结构、出处、宣传性、可核查性不足

### US-4：批量评估多段文本

作为内容运营，我希望一次评估多段文本，快速找出最差的几段优先修改。

**验收标准**：
- 用户一次输入多段文本
- 系统创建批量任务
- 输出批量总览报告和批量评分明细表
- 用户能按分数和风险维度筛选低分项

### US-5：批量评估多个网页

作为 AEO 负责人，我希望一次评估多个网页 URL，查看整批内容资产的整体质量和高风险项。

**验收标准**：
- 用户一次输入多条 URL
- 系统按受控并发抓取和评分
- 输出总览报告和明细表
- 当部分 URL 失败时，仍可交付其余结果

## 6. 方案概述

### 6.1 产品形态

该能力以“新分析任务”的方式嵌入现有工作台：

1. **Chat 发起任务**
2. **WebSocket 推进执行进度**
3. **Canvas 承载正式报告**
4. **ArtifactNav 展示交付物**

### 6.2 核心原则

1. 不新增新的一级页面
2. 不打破当前 `report / dataTable` 交付体系
3. 先单条，后批量
4. 批量场景采用“总览 + 明细 + 按需详情”三层结构

## 7. 输入类型定义

| 类型 | 标识 | 说明 |
| :--- | :--- | :--- |
| 单条引用 URL | `citation_url` | 来自 A4 抓取结果的引用链接 |
| 单条网页 URL | `user_url` | 用户直接输入的网页地址 |
| 单条文本 | `user_text` | 用户直接输入的单段文本 |
| 批量 URL | `batch_url` | 用户一次输入多条 URL |
| 批量文本 | `batch_text` | 用户一次输入多段文本 |

## 8. 评分模式

### 8.1 AICE-Web

适用于网页 URL 与引用链接。

评估维度：

1. C6 Coverage
2. C9a Semantic Tagging
3. C9b Schema Usage
4. C8 Timeliness
5. C1 Credibility
6. C4 Claim Balance
7. C2 Consistency
8. C3 Checkability
9. C5 Clarity
10. C7 Intent Match

### 8.2 AICE-Text

适用于用户直接输入的文本。

映射规则：

1. C6 -> 输入材料完整度
2. C9a -> 文本结构化程度
3. C9b -> 来源元信息完整度
4. 其余维度保持原义

### 8.3 报告要求

无论网页还是文本，都必须在报告中明确标注：

- 评分模式
- 总分算式
- 总分解释

## 9. 交互流程

## 9.1 单条评估流程

```text
用户发起评估
  ->
系统识别 source_type
  ->
Chat 展示评估对象说明
  ->
A7 执行：抽取 -> 评分 -> 生成建议
  ->
Chat 返回摘要
  ->
Canvas 打开单条评估报告
```

## 9.2 批量文本流程

```text
用户一次输入多段文本
  ->
系统切分为多个 item
  ->
逐条执行 AICE-Text
  ->
聚合结果
  ->
Canvas 输出：批量总览报告 + 批量评分明细表
  ->
用户点开单项详情
```

## 9.3 批量网页流程

```text
用户一次输入多条 URL
  ->
系统创建 batch_evaluation
  ->
限流并发抓取正文与结构信息
  ->
逐条执行 AICE-Web
  ->
聚合成功项与失败项
  ->
Canvas 输出：批量总览报告 + 批量评分明细表
  ->
用户按需查看单项报告或重试失败项
```

## 10. 报告输出设计

## 10.1 单条评估报告

统一复用 `report` 类型，新增：

- `report_kind = content_evaluation`

单条报告至少包含：

1. 总分与档位
2. 算式验证区块
3. 维度得分明细
4. 容易被 AI 采信的原因
5. 需审慎对待的原因
6. 修改建议
7. 证据锚点

## 10.2 批量总览报告

统一复用 `report` 类型，建议：

- `report_kind = content_evaluation_batch`

总览报告至少包含：

1. 本批次总数 / 成功数 / 失败数
2. 平均分 / 中位分 / 最低分
3. 低分维度分布
4. Top 风险项
5. 批量优化建议摘要

## 10.3 批量评分明细表

统一复用 `dataTable` 类型。

至少字段：

1. `item_id`
2. `source_type`
3. `title_or_excerpt`
4. `overall_score`
5. `score_band`
6. `top_risk_dimension`
7. `status`
8. `detail_artifact_id`

## 10.4 Prompt 产物要求

虽然 PRD 不展开具体实现细节，但本需求要求研发交付时必须具备明确的 Prompt 约束，而不能只依赖自由生成。

### 单条评估 Prompt 必须保证

1. 明确区分 `AICE-Web` 与 `AICE-Text`
2. 明确使用固定 9C 权重矩阵，而不是自由解释
3. 明确输出每个维度得分
4. 明确输出总分求和算式
5. 明确输出“容易被 AI 采信”与“需审慎对待”
6. 明确输出至少 2 条可执行修改建议
7. 明确输出每个维度的 `confidence`
8. 输出严格 JSON，便于前端稳定渲染

### 单条评估 Prompt 必须执行的硬规则

1. 页面不可读时，`C6 = 0`
2. 缺失 H1 或关键结构标签时，`C9a` 至少扣 5 分
3. 未发现 Schema 标记时，`C9b` 至少扣 5 分
4. 每个维度都必须给出评分逻辑与扣分原因
5. 总分必须等于各维度求和结果

### 批量聚合 Prompt 必须保证

1. 逐条 item 先有标准化结果
2. 聚合层再生成批量总览结论
3. 明细表与总览报告字段口径一致
4. 失败项保留失败原因，不得静默丢失
5. 每个 item result 保留 `overall_confidence`，便于后续排序和降级展示

## 10.5 单条报告字段级要求

单条报告至少包含以下结构化字段：

1. `report_kind`
2. `evaluation_mode`
3. `overallScore`
4. `scoreBand`
5. `source`
6. `formula`
7. `dimension_scores`
8. `trusted_reasons`
9. `caution_reasons`
10. `recommendations`
11. `evidence`
12. `overall_confidence`

这些字段缺一不可，否则前端无法稳定渲染完整报告。

## 10.6 批量产物字段级要求

### 批量总览报告至少包含

1. `report_kind = content_evaluation_batch`
2. `batch_summary`
3. `dimension_distribution`
4. `top_risks`
5. `batch_recommendations`

### 批量明细表至少包含

1. `item_id`
2. `status`
3. `overall_score`
4. `top_risk_dimension`
5. `detail_artifact_id`
6. `failure_reason`（失败项必填）
7. `overall_confidence`（成功项必填）

## 11. 技术方案要求

## 11.1 后端能力

需要新增：

1. `A7 Content Evaluation Agent`
2. 输入识别与路由
3. URL 内容抽取
4. AICE-Web / AICE-Text 评分器
5. 批量任务聚合器
6. 部分成功任务模型

## 11.2 Artifact 策略

当前固定 `{session_id}_{output_type}` 的策略不够用。

必须支持自定义 `artifact_id`。

建议：

1. 单条：`{session_id}_report_eval_{source_hash}`
2. 批量总览：`{session_id}_report_eval_batch_{batch_id}`
3. 批量表格：`{session_id}_datatable_eval_batch_{batch_id}`
4. 单项详情：`{session_id}_report_eval_item_{item_id}`

## 11.3 并发策略

1. 批量文本可较高并发
2. 批量网页默认并发 `3-5`
3. 必须支持超时、重试、降级
4. 单项失败不能拖垮整个批量任务

---

## 12. 关键产品决策

| 决策点 | 选择 | 原因 |
| :--- | :--- | :--- |
| 放在哪里 | Chat + Canvas | 最符合现有平台结构 |
| 报告类型 | 复用 `report` / `dataTable` | 降低改造成本 |
| 先做什么 | 单条评估 | 最快验证价值 |
| 批量先做哪个 | 批量文本 | 更稳定、实现成本更低 |
| 批量结果形态 | 总览 + 明细 + 按需详情 | 最容易消费 |
| URL 批量执行方式 | 限流并发 | 控制稳定性和时延 |

## 13. 成功指标

### 13.1 Phase 1

| 指标 | 目标 |
| :--- | :--- |
| 单条评估完成率 | >= 90% |
| 单条评估平均完成时间 | 文本 <= 30s，网页 <= 90s |
| 报告可读性反馈 | >= 80% 用户能理解扣分原因 |
| 修改建议可执行性反馈 | >= 70% 用户认为建议可直接使用 |

### 13.2 Phase 1.5 / 2

| 指标 | 目标 |
| :--- | :--- |
| 批量任务交付率 | >= 85% |
| 批量网页单项成功率 | >= 70% |
| 部分成功任务可用率 | >= 95% |
| 用户能快速识别 Top 风险项 | >= 80% 主观反馈 |

## 14. 验收标准

## 14.1 单条评估验收

1. 用户输入 URL 能正确进入网页评估流程
2. 用户输入文本能正确进入文本评估流程
3. 抓取结果中的引用支持触发评估
4. 单条报告包含总分、算式、维度明细、风险原因、修改建议
5. 同一来源重复评估时支持版本历史

## 14.2 批量文本验收

1. 用户一次输入多段文本，系统可切分为多个 item
2. 批量任务可输出总览报告和明细表
3. 明细表能定位到低分项
4. 用户可查看单项详情报告

## 14.3 批量网页验收

1. 用户一次输入多条 URL，可成功创建批量任务
2. URL 抓取采用受控并发
3. 单项失败不影响其他成功项交付
4. 总览报告和明细表可正确反映成功/失败状态
5. 失败项支持后续单独重跑

---

## 15. 风险与缓解

| 风险 | 严重度 | 缓解措施 |
| :--- | :--- | :--- |
| URL 抽取失败或反爬 | 高 | 降级为可访问性风险，并保留失败项状态 |
| 文本与网页评分可比性误解 | 中 | 报告显式展示评分模式 |
| Artifact 覆盖冲突 | 高 | 引入自定义 `artifact_id` |
| 批量任务中单项失败导致整批失败 | 高 | 采用部分成功模型 |
| 批量网页耗时过长 | 中 | 限流并发、超时控制、异步结果交付 |
| 明细过多导致用户无从下手 | 中 | 总览先给 Top 风险项和优先级 |

## 16. 实施建议

### 16.1 后端

1. 新增 A7 Agent
2. 扩展 Orchestrator 意图路由
3. 新增内容抽取与评分模块
4. 扩展 `events.py` 支持自定义 Artifact ID
5. 新增批量聚合执行能力

### 16.2 前端

1. `FetchResultsContent` 增加“评估此引用”
2. `ReportContent` 增加内容评估分支
3. 新建 `EvaluationReportContent`
4. 新建批量评分明细表适配
5. 支持从表格跳转单项详情

### 16.3 推荐上线顺序

1. 先上线单条 URL / 文本评估
2. 再上线批量文本
3. 最后上线批量 URL

这是最稳妥、最可验证价值的路径。
