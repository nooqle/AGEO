# 置信度信号交付物方案辩论纪要

**参与角色**: Marty Cagan / Don Norman / Martin Fowler / John Carmack / James Bach
**日期**: 2026-03-12
**状态**: 待决策
**议题**: 是否应以“置信度信号（Confidence Signal）交付物”为核心，替代此前以 Chat 为主入口的内容评估方案

---

## 1. 新提案定义

用户提出的新方案可以抽象为：

1. 在 A4 抓取答案完成后，系统自动从答案中的 citation URL 提取所有引用链接
2. 对这些链接统一执行 AICE 评估
3. 生成一个新的交付物：`置信度信号`
4. 该交付物展示每个引用链接的 AICE 评估结果
5. 交付物内部提供一个 `额外评估` 输入区
6. 用户可以像 NotebookLM 那样在该输入区粘贴：
   - 一个或多个链接
   - 一段文字
7. 提交后，不走复杂的 Chat 意图理解，而是直接在当前交付物上下文内触发新的评估并更新结果

这实际上不是“原方案的小改”，而是把内容评估从 `Chat 主入口能力`，改成 `A4 相关联的侧边交付物能力`。

---

## 2. 辩论问题

这次要解决的不是“能不能做评估”，而是：

1. 评估能力的主入口应该放在 Chat，还是放在专用交付物里
2. 主 LLM 是否还需要承担复杂的意图分类
3. 额外评估是否应该被约束在一个更局部、更明确的交互容器中

---

## 3. PM 观点（Marty Cagan）

### 支持点

从产品价值看，这个新方案比“在 Chat 里让用户主动发起评估”更聚焦，因为它把能力直接绑定到一个明确问题：

```text
A4 抓回来的答案，哪些引用来源更可信、更容易被 AI 采信？
```

这是强问题，不是泛功能。

它有三个明显优势：

1. 离用户的当前任务更近
   - 用户刚看完抓取结果，立刻就想知道这些 citation 靠不靠谱
2. 用户教育成本更低
   - “置信度信号”是与 A4 强相关的增量结果，不需要解释太多
3. 扩展动作自然
   - “额外评估”是同一个问题空间里的延伸，而不是跳到另一个任务世界

### 质疑点

如果把所有内容评估都收进这个交付物，可能会牺牲一个价值场景：

- 用户没有先做 A4，只是单纯想拿一篇文章或一段稿子做评估

所以产品上更合理的方式不是完全删除 Chat 路径，而是：

- `置信度信号交付物` 成为主路径
- Chat 评估成为次路径或后续能力

### PM 结论

我支持把“置信度信号交付物”升级为内容评估的主承载方案，因为它更像一个用户真正需要的产品，而不是一个到处都能触发的功能。

---

## 4. UX 观点（Don Norman）

### 支持点

从心智模型上，这个方案明显更顺。

原来方案的问题在于：

1. 用户要记得“这个能力存在于 Chat 里”
2. 用户要猜系统会不会把输入理解成评估而不是抓取
3. 用户要在全局输入框里切换任务模式

这会制造不必要的认知负担。

新的方案把交互改成：

```text
先看抓取结果
  -> 再看引用来源的置信度信号
  -> 再决定是否做额外评估
```

这个流程符合用户自然的注意力顺序。

### UX 风险

如果“额外评估”只是一个隐蔽的小按钮，再弹出一个自由输入框，用户仍然会迷失。

所以这个方案要成立，必须满足：

1. `置信度信号` 本身是一个独立、明确、可命名的交付物
2. `额外评估` 的输入框必须是强 signifier
3. 输入框上必须写清允许输入什么：
   - 粘贴链接
   - 粘贴文本
4. 提交后的反馈必须非常清楚：
   - 正在评估 1 个链接
   - 正在评估 1 段文本
5. 新结果应该追加到当前交付物的结构中，而不是悄悄替换旧结果

### UX 结论

我支持这个方案，但前提是它必须被设计成“在同一个概念容器中持续扩展”的体验，而不是在 Artifact 里再塞一个迷你 Chat。

---

## 5. 架构师观点（Martin Fowler）

### 支持点

从架构角度，我认为这个方案最大的价值在于：

**它把原本复杂的全局意图路由问题，降级为局部上下文内的确定性动作。**

也就是说：

- 在 Chat 里，系统必须猜“这是文章评估还是自定义问题”
- 在 `置信度信号` 交付物里，系统只需要处理“新增一个评估输入”

这是两个完全不同级别的复杂度。

### 架构收益

1. 降低 Orchestrator 的路由负担
2. 减少主 LLM 的意图分类职责
3. 让 A7 的触发条件更明确
4. 把 citation 评估与 A4 结果建立稳定关联

### 架构风险

这个方案会引入一个新的架构要求：

**Artifact 不再只是静态结果，而变成可交互、可追加更新的工作面板。**

这意味着我们需要回答：

1. 交付物内部输入如何触发后端任务
2. 更新结果如何合并回同一个 Artifact
3. 历史版本和追加结果如何共存
4. 如果用户先评 citation，再评额外 URL / 文本，数据模型如何统一

这不是坏事，但它意味着复杂度从 Chat 路由层，转移到了 Artifact 交互层。

### 架构结论

我支持这个方向，而且我认为它比“在 Chat 里做大量分流逻辑”更贴近你原始想要的架构。

但我会强调一个原则：

- 不要先做一个全新一级 Canvas 类型
- 先把它落成 `report_kind = confidence_signal` 或 `dataTable + report` 的组合
- 用最小改动验证这个交付物是否真的承担起主要入口职责

---

## 6. 工程观点（John Carmack）

### 支持点

如果目标是降低系统复杂度，我更偏向这个新方案。

原因很简单：

- Chat 方案需要改 Orchestrator、Prompt、Guard Rules、ask_user、输入识别
- 交付物方案把绝大多数复杂判断拿掉了

在交付物里，输入动作天然被约束成：

- 评估一个链接
- 评估一段文本

这比在全局 Chat 框里猜用户是不是想抓取问题稳定得多。

### 工程代价

但这并不意味着“更便宜”。它的代价换了位置：

1. 前端要支持 Artifact 内嵌输入区
2. 前端要支持局部 loading、局部错误、局部更新
3. 后端要支持“针对某个 Artifact 的增量更新任务”
4. Artifact store 要支持同一交付物里追加 item，而不是只替换 data

### 工程判断

如果二选一：

- `复杂 Chat 路由`
- `可交互 Artifact`

我会选后者，因为它更局部、更可测，也更可控。

### 工程结论

我支持这个新方案作为主线，但建议收敛成下面这个 MVP：

1. A4 完成后自动生成 `置信度信号` 交付物
2. 先只展示 citation 链接评分列表
3. 再加 `额外评估` 输入框
4. 输入框只支持两类输入：
   - URL
   - 纯文本
5. 不支持在这个输入框里输入“自定义问题”或其它分析命令

这样边界最清楚。

---

## 7. QA 观点（James Bach）

### 支持点

这个新方案的可测性比 Chat 路由方案更好，因为上下文更封闭。

在 Chat 里很难穷举所有说法：

- “帮我分析这个链接”
- “看看这篇文章”
- “这些内容怎么样”
- “用这些问题测一下”

这种语言歧义会让测试边界持续膨胀。

而在交付物输入区里，我们可以把用户允许做的事情明确限制住。

### QA 风险

我关心 4 类问题：

1. 用户粘贴混合输入
   - 一个 URL + 一段文字
2. 用户连续触发多次额外评估
3. Artifact 增量更新后顺序混乱
4. A4 citation 自动评估和用户手动追加评估混在一起时，用户分不清来源

### QA 结论

我支持这个方向，因为它更容易建立清晰的错误边界和测试边界。

但必须在 UI 和数据层显式区分：

- `自动来源评估`
- `手动追加评估`

否则用户会混淆结果来源。

---

## 8. 辩论结论

### 8.1 一致共识

五个角色的共识是：

1. 这个方案确实能显著缓解我们之前对 Chat 层复杂度的担忧
2. 它更贴近 A4 结果消费场景
3. 它让内容评估从“全局语言理解问题”变成“局部明确动作问题”
4. 它应该成为 citation 评估的主方案

### 8.2 仍然保留的分歧

唯一需要保留的分歧是：

- 是否彻底废弃 Chat 入口

当前更稳妥的结论不是“彻底推翻 Chat 方案”，而是：

1. `置信度信号交付物` 作为主路径
2. Chat 入口降级为后续补充能力
3. MVP 阶段不要新增一套显式的 Chat 意图分类模块；若用户在输入框中粘贴链接或文本，仍可由主 LLM 在受限上下文中直接判断并驱动 A7

---

## 9. 新的推荐架构

### 推荐方案

```text
A4 抓取完成
  -> 提取 citation URLs
  -> A7 批量执行 citation AICE
  -> 生成“置信度信号”交付物
  -> 用户在交付物内点击“额外评估”
  -> 输入 URL 或文本
  -> A7 执行增量评估
  -> 更新同一个交付物
```

### 为什么更好

1. 主链路更简单
2. 用户心智更稳定
3. 意图判断复杂度显著下降
4. 评估上下文与 A4 结果强关联
5. 额外评估成为交付物内的受限动作，而不是全局自然语言理解问题

---

## 10. 对原方案的影响

这不会让之前的工作完全作废。

可以保留的部分：

1. A7 评分矩阵
2. Prompt 设计
3. 结构化输出 schema
4. 单条 / 批量评估结果模型
5. Artifact ID 问题和恢复问题
6. 前端 `report_kind` 分支思路

需要重构的部分：

1. Chat-first 入口不再是主设计
2. 主 LLM 意图判断从主链路降级为补充方案
3. 批量网页 / 文本入口要先让位于 `置信度信号` 交付物设计

---

## 11. 最终建议

我的建议不是“推翻之前所有方案”，而是做一次架构收敛：

### 新 MVP

1. A4 完成后自动生成 `置信度信号` 交付物
2. 交付物内展示 citation 列表及每条 AICE 结果
3. 交付物内提供 `额外评估` 输入框
4. 输入框仅支持：
   - URL
   - 文本
5. 提交后增量更新同一交付物

### 暂缓内容

1. Chat 中独立实现一套复杂、显式的规则型意图分类服务
2. 在同一个入口里同时支持“评估”和“自定义问题抓取”
3. 在 `额外评估` 输入框里开放与评估无关的其它任务类型

### 一句话结论

**如果你真正担心的是 Chat 层逻辑被做复杂了，那这个“置信度信号交付物”方案比之前的 Chat-first 方案更贴近你的原始架构意图，而且我认为应该改为主方案。**
