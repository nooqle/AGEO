# Specta AI 架构升级路线图（对标企业级智能体平台）

> 版本：v1.0  
> 日期：2026-03-06  
> 目的：记录从当前 Specta AI 架构演进到“可治理、可扩展、可平台化”架构的执行路径。  
> 对标参考：`安利 App 大A助手智能体系统架构设计文档`（2026-03，30页）。

---

## 1. 背景与范围

当前系统已具备可运行闭环（A1-A5 + Orchestrator + LangGraph + WebSocket + Canvas），但与企业级多智能体平台相比，仍存在三类差距：

1. 治理能力不足：缺少独立的全链路合规中间层与统一审计标准。
2. 平台能力不足：长期记忆、工具治理、沙箱策略未形成统一平台抽象。
3. 交互协议不足：前端以固定内容类型渲染为主，尚未形成 A2UI 式声明式协议。

本路线图聚焦“升级路径”，不做大爆炸重构。

---

## 2. 升级目标

1. 从“可运行”升级为“可治理”。
2. 从“单场景产品”升级为“能力平台”。
3. 在不破坏现有 AEO 主链路的前提下，支持多业务域 Agent 扩展。

---

## 3. 非目标

1. 不一次性引入完整企业平台全部模块（避免过度设计）。
2. 不重写现有 A1-A5 流程与前端核心交互。
3. 不在单个迭代内同时改造编排、记忆、工具、前端协议四大块。

---

## 4. 分阶段路线图（6个月）

## Phase 1（0-6周）：稳定与治理

### 目标
- 建立可追溯、可回滚、可审计的执行体系。

### 关键交付
1. 合规与风控中间层（事前/事中/事后钩子）。
2. 统一审计事件规范（调用、确认、失败、重试、降级）。
3. 编排策略保护栏（高风险工具必须确认，失败分级处理）。
4. 主链路稳定性看板（成功率、重试率、人工介入率、时延）。

### 验收指标
1. 核心主链路成功率 > 95%。
2. 高风险操作审计覆盖率 100%。
3. 失败场景具备统一降级路径（无静默失败）。

---

## Phase 2（7-14周）：平台化底座

### 目标
- 将记忆、工具、执行环境从“功能实现”升级为“平台能力”。

### 关键交付
1. 统一记忆抽象：`user/session/agent` 三层记忆接口。
2. Tool Registry + 权限策略：工具可插拔、可授权、可审计。
3. 沙箱策略中心：网络白名单、命令分级、资源配额统一配置。
4. 监测与任务统一策略（在线/离线/headless 行为一致）。

### 验收指标
1. 记忆读取命中率和误召回率可观测。
2. 工具调用 100% 经过策略引擎。
3. 沙箱高风险动作默认拦截并可追溯。

---

## Phase 3（15-24周）：交互协议与多域扩展

### 目标
- 形成可扩展交互协议与多业务域 Agent 扩展模板。

### 关键交付
1. A2UI 增量协议（先覆盖报告卡、确认卡、进度卡）。
2. 快慢车道路由（规则快车道 + 规划慢车道）。
3. 多域子 Agent 模板（接入规范、输入输出契约、评测基线）。
4. 可灰度发布与回滚机制（按 agent/tool/protocol 分开灰度）。

### 验收指标
1. 核心体验 P95 响应时延下降。
2. 服务可用性达到 99.9% 目标。
3. 新增子 Agent 接入周期显著缩短（模板化接入）。

---

## 5. 模块级实施映射（对应现有仓库）

1. 编排层  
- 位置：`aeo-platform/backend/app/workflow/orchestrator_node.py`、`graph.py`  
- 动作：新增 policy hook、失败分类、确认策略守卫。

2. 事件与审计层  
- 位置：`aeo-platform/backend/app/workflow/events.py`  
- 动作：统一审计字段、风险标签、调用链 trace 规范。

3. 状态与记忆层  
- 位置：`aeo-platform/backend/app/workflow/state.py`、`services/snapshot_service.py`  
- 动作：抽象长期记忆接口，保持与现有 checkpoint/snapshot 兼容。

4. 工具与执行层  
- 位置：`aeo-platform/backend/app/workflow/nodes_a4.py`、`app/core/fetchers/*`  
- 动作：工具注册、权限校验、沙箱策略集中化。

5. 前端协议层  
- 位置：`frontend/src/types/canvas.ts`、`frontend/src/stores/canvasStore.ts`  
- 动作：在现有内容模型上增量引入声明式协议字段与渲染映射。

---

## 6. 实施策略

1. 双轨推进：业务迭代与架构升级并行，但通过 feature flag 隔离。
2. 小步快跑：单 PR 单主题，控制改动范围，保留回滚点。
3. 主链路优先：优先改造 A1->A5 主分析链，追问/监测后续跟进。
4. 强约束验收：每阶段必须有可量化指标与故障演练记录。

---

## 7. 风险与缓解

1. 风险：升级影响现有稳定性。  
缓解：开关灰度、逐模块回滚、主链路回归测试先行。

2. 风险：中台化过度导致交付变慢。  
缓解：严格按阶段目标交付，不提前实现下一阶段能力。

3. 风险：协议改造牵动前后端联动。  
缓解：先做兼容字段，后做渲染切换，始终保留旧协议路径。

---

## 8. 首两周执行清单（立即落地）

1. 定义“风控与审计事件规范”（字段、等级、拦截动作、保留周期）。
2. 在 orchestrator tool call 前后接入统一 policy hook（不改业务语义）。
3. 建立架构看板：成功率、重试率、人工介入率、任务耗时。
4. 试点接入两个节点：`answer_fetch` 与 `data_analytics`。

---

## 9. 里程碑

1. M1（第6周）：治理闭环完成，主链路稳定上线。  
2. M2（第14周）：平台底座完成，记忆/工具/沙箱可统一治理。  
3. M3（第24周）：协议化与多域扩展完成，进入平台化迭代阶段。
