# PRD 评审：品牌圈层图谱与可操作画布改版

> 评审对象：`prd-brand-circle-board-redesign-2026-06-17.md`
> 评审日期：2026-06-17
> 评审结论：核心方向正确，但概念之间的连接规则和边界条件不完整，存在 3 个阻断级问题需要在 Phase 0 解决。

---

## 一、核心逻辑漏洞（阻断级）

### 1. 圈层分配算法完全空白

PRD 定义了 6 个圈层（中心/内圈/中圈/外圈/竞品圈/风险圈），数据模型有 `connection_strength` 和 `circle_zone` 字段，但：

- **没有定义实体如何被分配到圈层**。什么强度阈值对应内圈 vs 中圈？平台覆盖率多少算"稳定连接"？
- **`connection_strength` 是连续值还是分级？** 计算公式是什么？评分维度和权重是什么？
- **圈层迁移条件未定义**。中圈实体需要什么条件才能升级到内圈？外圈实体什么时候降级？

**风险**：这是整个产品的核心计算引擎，没有它就无法生成有意义的 Graph。如果 Phase 5 才开始定义，前面的 Demo 都是空转。

**建议**：Phase 0 补充圈层分配规则文档，至少定义评分维度、权重、阈值区间和迁移条件。

### 2. Graph Patch 冲突解决缺失

PRD 定义了 16 种 Graph Patch 事件，但：

- **多个 Board 同时运行时，产生冲突 Patch 怎么办？** 例如 Board A 识别实体 X 为"战略目标"，Board B 识别同一实体为"竞品占位"。
- **先后顺序如何处理？** 如果先应用了 Board A 的 Patch，Board B 的 Patch 应该覆盖还是排队？
- **用户审阅队列是 per-Graph-Update 还是全局？** 如果全局，不同 Board 的审阅项如何区分？

**风险**：多人/多画布场景下，图谱可能变得不一致。

**建议**：定义 Graph Patch 优先级规则（如后覆盖前、人工审阅优先于自动、冲突项进入审阅队列），并明确审阅队列的作用域。

### 3. 实体关系抽取节点是黑箱

"实体关系抽取"节点是最关键的节点——它把 AnswerSet + EntityLexicon 转为 EntityRelationSet + Graph Patch。但：

- **抽取逻辑的输入边界不清晰**：EntityLexicon 的"推荐关系类型"是什么？类型列表有哪些？
- **关系强度如何从文本回答中计算？** 是基于共现频率？上下文语义？显式提及？还是 LLM 判断？
- **实体消歧规则未定义**：当 AI 回答中出现"纽崔莱"和"Nutrilite"时，是否自动合并？阈值是什么？

**风险**：这个节点承载了从非结构化数据到结构化图谱的全部转换逻辑，但没有任何技术规格。实施时极可能出现"每个开发者理解不同"的问题。

**建议**：为实体关系抽取节点单独写一份技术规格，定义关系类型枚举、强度计算方法、消歧策略。

## 二、架构冲突（需要产品决策）

### 4. Board 节点编排 vs. 现有 Orchestrator 的矛盾

现有系统用 LLM-driven Orchestrator + Function Calling 动态路由 Agent。新 PRD 用静态节点链（Board）做编排。两种范式根本不同：

- **Orchestrator 还在不在？** 如果不在，谁负责动态决策（比如 A4 抓取失败后要不要换策略）？
- **如果 Orchestrator 仍在，它和 Board 的关系是什么？** Orchestrator 变成 Board 的"运行器"？还是 Board 的某个"智能节点"？
- **现有 A1-A6 的 Agent 代码如何映射到 Node？** 每个 Agent 直接变成一个 Node？还是 Agent 的某个能力切片变成 Node？

**建议**：Phase 0 明确 Orchestrator 在新架构中的定位。至少需要回答：谁驱动 Board 执行？谁处理 Board 内部的运行时异常？谁在节点失败时做重试/降级决策？

### 5. 向后兼容与数据迁移空白

现有系统有 Sessions、Messages、Canvas Artifacts、Snapshots 等数据实体。PRD 定义了全新的 Brand Space / Graph / Boards / Assets / Reports 架构，但：

- **现有 Chat 会话中的品牌分析数据如何迁移？**
- **已有的 Canvas Artifacts（workflow、questionList、fetchResults、report）映射到新架构的哪里？**
- **现有 Snapshot 模型和新的 Graph Update 是什么关系？**
- **用户创建的已有 Session 如何在新架构中展现？**

**建议**：至少需要一份数据映射表（旧实体 → 新实体），并决定是双系统并行过渡还是一刀切换。

### 6. "不做低代码平台" vs. 实际功能列表的矛盾

PRD 明确说"不把产品做成通用低代码工作流平台"，但要求：
- 添加/删除/替换/连接节点
- 校验节点输入输出兼容性
- 运行单节点/整张画布/从失败节点继续

这**就是**低代码工作流平台的核心能力。自相矛盾会导致：
- 要么做得不够（节点编排不完整，用户困惑）
- 要么做过头（变成通用编排器，偏离品牌情报核心）

**建议**：重新定义边界——"模板驱动的有限编排"vs"自由组合的无限编排"。明确哪些编排能力开放、哪些锁定在模板内。

## 三、UX 与用户旅程缺陷

### 7. 新用户 Onboarding 完全缺失

"新品牌初始化"旅程假设用户已经知道什么是"品牌圈层图谱"、为什么要"导入品牌资料"、"实体词表"是什么。但缺少：

- 空 Graph 的空状态设计
- 引导式品牌创建流程
- 渐进式概念暴露（progressive disclosure）
- 新手教程或示例品牌

**建议**：补充空状态设计稿和引导流程，至少覆盖"首次进入空白品牌空间"的体验。

### 8. Chat 降级后的冷启动问题

PRD 把 Chat 降级为"上下文命令层"，但现有用户唯一的品牌分析入口就是 Chat。没有定义：

- **用户如何不用 Chat 创建第一个品牌？** 直接在 Dashboard 点"新建品牌"？但没有定义这个交互。
- **用户如何不用 Chat 发起第一次全景抓取？** 在 Boards 里选模板？但新用户不知道选什么模板。
- **全局入口在哪？** PRD 待确认问题第 8 条问到了但没有答案。如果只有选中对象才能触发 Chat，新用户在空品牌空间里没有任何可选中对象。

**建议**：定义品牌空间的非 Chat 入口操作流，确保空白状态下用户也能完成首次操作。

### 9. 节点编排对目标用户可能过于复杂

用户旅程中描述"删除问题模拟节点 → 拖入手动上传问题列表节点"。目标用户是品牌经理和营销团队，不是工程师。缺少：

- 引导模式（guided mode）vs 专家模式（expert mode）
- 防止用户创建无效 Board 的 guardrail
- 节点兼容性校验的错误提示和修复建议

**建议**：为 Phase 3（节点可替换）设计引导模式，让用户在模板基础上做有限修改，而非从空白画布开始编排。

## 四、规格不完整

### 10. Node I/O Schema 缺失

PRD 用名称定义了 Node 的输入输出（BrandSeed、QuestionSet、AnswerSet 等），但没有定义数据结构。这是节点组合模型的契约基础——没有它：

- 兼容性校验无法实现
- 节点替换的"类型兼容"无法判定
- 下游开发会有无数对齐问题

**建议**：为每个 I/O 类型定义 JSON Schema 或 TypeScript interface，作为节点契约文档。

### 11. 报告生成逻辑未定义

PRD 定义了报告结构，但没定义谁生成报告、如何生成：

- "报告解读"节点是用 LLM 生成文本？还是用模板填充结构化数据？
- Graph Update 的变化量很小时（如只有 1 个实体微调），报告应该多长？
- 报告的"建议下一张画布"从何而来？是 LLM 推理还是规则匹配？

**建议**：至少明确报告生成的技术方案（LLM 生成 vs 模板填充 vs 混合），并定义报告长度与变化量的关系规则。

### 12. 监控模板过于粗略

周期监控模板只有一个 6 步流程，但缺少：

- 调度策略（Cron 表达式？间隔？）
- 触发条件（什么变化值得通知？）
- 通知渠道（应用内？邮件？微信？）
- 失败重试策略
- 与现有 `MonitoringPlan` 模型的关系

**建议**：监控模板应该作为独立 PRD 或本 PRD 的附录，补充调度、通知、重试的完整规格。

### 13. 实体审阅工作流不完整

审阅动作定义了接受/拒绝/合并/改名/移入风险圈/标记战略目标，但：

- **拒绝后实体去哪？** 从图谱删除？进入黑名单？
- **合并后原实体的历史数据如何处理？** 连接强度重新计算？
- **审阅决策是否可撤销？** 没有 Undo 机制。
- **批量审阅**如何操作？逐条审阅在大规模更新下不可行。

**建议**：补充审阅状态机（pending → accepted/rejected/merged，以及后续回退路径），并定义批量操作机制。

## 五、实施风险

### 14. Phase 顺序有 Demo 陷阱

Phase 1-4 全部用模拟数据，Phase 5 才接入真实 A4/A5。这意味着：

- 用户在 Phase 2-4 体验到的"动态感"全部是假数据，真实的 AI 回答可能远没有 Demo 那么干净
- 实体抽取质量只有在 Phase 5 才能验证，但这是整个产品的命脉
- 如果 Phase 5 发现抽取质量不足，前面的 Graph/Board/Diff/Report 全部基于错误假设

**建议**：Phase 2 就应该用至少一个真实平台做端到端验证，哪怕只有一个节点。具体做法：在 Phase 2 中加入一个"真实抓取验证子阶段"，用 1 个品牌 × 1 个平台 × 10 个问题跑完整个链路。

### 15. 图渲染技术选择未定

圈层图谱不是标准力导向图，需要自定义布局。PRD 待确认问题第 1 条问"圈层布局 vs 力导向双模式"，但这是技术选型的核心：

- D3.js：灵活但性能有限（100+ 实体时可能卡顿）
- Cytoscape.js：专业图可视化，但圈层布局需自定义
- Canvas/WebGL：高性能但交互开发成本高
- React Flow：已有类似能力，但更适合 Board 而非 Graph

**建议**：在 Phase 0 或 Phase 1 初期完成技术选型 POC，不要留到实施阶段。

### 16. Graph Patch Stream 性能未考虑

16 种事件在全量抓取时（4 平台 × 50+ 问题 × 多轮抽取）可能产生数百到上千事件。缺少：

- 节流（throttling）策略
- 批量更新（batching）机制
- 前端渲染优化（虚拟化/增量更新）

**建议**：定义事件批处理窗口（如 200ms 内的事件合并推送）和前端渲染节流策略。

---

## 六、关键遗漏

### 17. 缺少数据保留与清理策略

Assets 会无限增长，Graph Update 会不断堆积。没有：

- 旧资产归档策略
- 数据删除/清理规则
- 存储成本控制

**建议**：定义资产保留周期和自动归档规则。

### 18. 缺少协作模型

一个品牌是否只有一个人操作？如果多人协作：

- 谁能审阅实体？
- 谁能修改 Board？
- Graph Update 是否需要审批流程？

**建议**：至少在 Phase 0 明确"第一版单人操作"还是"多角色协作"。如果单人，后续版本再考虑协作。

## 优先级总结

| 优先级 | 编号 | 问题 | 原因 |
|--------|------|------|------|
| **P0** | 1 | 圈层分配算法空白 | 整个产品依赖此计算，无它则 Graph 无意义 |
| **P0** | 4 | Board 与 Orchestrator 关系未定义 | 架构冲突不解决，实施无法开始 |
| **P0** | 2 | Graph Patch 冲突解决缺失 | 多画布场景下图谱不一致 |
| **P1** | 10 | Node I/O Schema 缺失 | 没有契约，节点组合模型无法实现 |
| **P1** | 3 | 实体关系抽取节点是黑箱 | 最关键节点无规格，实施必然跑偏 |
| **P1** | 14 | Phase 顺序有 Demo 陷阱 | 尽早验证抽取质量，避免全链路返工 |
| **P1** | 8 | Chat 降级后的冷启动问题 | 新用户无法完成首次操作 |
| **P2** | 5 | 向后兼容与数据迁移 | 旧数据断层或双系统并行 |
| **P2** | 6 | "不做低代码"矛盾 | 边界不清导致功能膨胀或不足 |
| **P2** | 9 | 节点编排对用户过于复杂 | 目标用户可能无法使用 |
| **P2** | 7 | 新用户 Onboarding 缺失 | 用户无法理解新概念 |
| **P2** | 11 | 报告生成逻辑未定义 | 报告质量无法保证 |
| **P2** | 13 | 实体审阅工作流不完整 | 审阅闭环不完整 |
| **P2** | 15 | 图渲染技术未选型 | 影响整个 Graph 页面架构 |
| **P3** | 12 | 监控模板过于粗略 | 可后续版本完善 |
| **P3** | 16 | Patch Stream 性能 | 可实施时优化 |
| **P3** | 17 | 数据保留策略 | 可后续版本补充 |
| **P3** | 18 | 协作模型 | 第一版可限定单人 |
