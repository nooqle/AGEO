# 报告写作原则

本文档用于约束 Specta AI 在分析报告、诊断总结、设计说明中的写法。目标不是“写得像 AI 很完整”，而是“写得像人类，读者能快速抓住事实、判断和动作”。

## 1. 先回答业务问题

每一节都应该先回答一个明确问题，而不是先解释系统在做什么。

- 执行摘要回答：现在整体处于什么状态。
- 可见度分析回答：品牌有没有被提到，被提到以后算不算优势。
- 链接可见度分析回答：品牌露出最后流到了哪里，官网有没有接住。
- 问题解析回答：哪些问题里表现好，哪些问题里掉分，具体掉在哪。
- 情感与风险解析回答：用户和模型当前在反复强化什么认知。
- 平台偏好分析回答：不同平台的写法、来源偏好、先在哪个平台验证动作。
- 行动建议回答：先做什么，为什么先做，看什么指标判断有没有起效。

禁止写法：

- “本节只回答……”
- “这一节主要展示……”
- “先看……再看……”

这些句子通常只是解释结构，不提供新的业务信息。

## 2. 先事实，再判断，再动作

推荐的基本顺序：

1. 事实：客观数字、状态、样本
2. 判断：这意味着什么
3. 动作：下一步最值得做什么

不要反过来写。先给空泛建议，再回头找理由，会让内容显得虚。

## 3. 不创造新概念

报告里不应该出现内部分类词、分析器术语、工程抽象词，除非用户已经明确接受这套概念。

优先使用用户能立即理解的说法，例如：

- “横向比较类问题”
- “家庭场景选车问题”
- “价格与成本”
- “服务与便利性”

避免使用：

- 系统内部标签
- agent / analyzer / skill 术语
- 临时发明的命名
- 看起来高级、实际上没有公共语义的说法

判断标准：

- 如果读者第一反应是“这是什么意思”，这就不是好概念。

## 4. 加粗只服务重点

加粗不是装饰，只用于帮助人快速扫读。

默认规则：

- 关键数字加粗
- 极少数结论词加粗
- 不要把整句都加粗
- 不要把“标签 + 数字”一起粗到抢掉重点

推荐写法：

- `品牌可见度 **73.1%**`
- `官网引用转化率 **0.0%**`

不推荐写法：

- `**品牌可见度：73.1%**`
- `**当前最重要的判断是……**`

如果一段里有太多粗体，等于没有重点。

## 5. 标题只负责层级

H1 / H2 / H3 只用来表达结构，不承担“视觉强调”。

推荐用法：

- `#` 报告标题
- `##` 一级分析模块
- `###` 子问题或子板块

禁止用标题做这些事情：

- 模拟提示框
- 代替结论句
- 用来放口号式文案

## 6. 原问题和原答案用引用块

只要在展示原问题、原答案、原表述样本，就优先使用 Markdown 引用块。

推荐用法：

> 原问题

> 典型表述

这样做的原因：

- 读者一眼就能分清“分析结论”和“原始证据”
- 导出到 PDF 时也更稳
- 不需要依赖复杂样式

禁止把原样本直接塞进长句里，尤其不要用粗体问题文本来伪装重点。

## 7. 表格克制使用

报告正文默认不用表格。

表格只适合：

- 精确对照
- 密集枚举
- 确实需要横向比对的清单

在大多数诊断报告里，自然语言比表格更有信息密度，因为人类读者更关心：

- 这说明什么
- 哪几个最重要
- 为什么是它们

而不是自己在表格里做二次总结。

## 8. 多写结论句，少写结构说明

每个模块都应该有一句真正的结论句。

好的结论句：

- “理想汽车已经进入答案，但还不是默认答案。”
- “官网没有接住已经拿到的品牌露出。”
- “当前掉分主要发生在价格和家庭场景问题。”

差的结论句：

- “本节展示品牌在不同问题中的表现。”
- “以下是平台差异分析。”

前者帮助决策，后者只是目录说明。

## 9. 行动建议必须回到 EEAT

行动建议不许空泛。

每条建议至少要包含四件事：

- 事实是什么
- 这说明了什么机会
- 先做哪件事
- 看什么指标判断是否见效

推荐结构：

`事实 -> 动作 -> 验证指标`

例如：

- 现在有 19 条答案提到品牌，但 0 条引用官网。
- 先把价格对比、车型差异、家庭场景改成官网结论页。
- 先看官网引用转化率和品牌相关链接数有没有抬起来。

## 10. 避免典型 AI 句式

重点避免：

- “不是……而是……”
- “如果只保留一个最重要的判断……”
- “最值得记住的三个判断……”
- “先做最容易见效的事……”
- “本节主要展示……”
- “当前需要关注的是……”

这些句式的问题不在于绝对错误，而在于太像模板，容易把真实判断写平。

## 11. 句子要像人在说话

人类写法通常有这些特点：

- 先说结果
- 再补最重要的依据
- 句子长短有变化
- 不会每段都同一个开头

所以应该：

- 少写整齐对称的模板句
- 少写口号式总结
- 少写空泛的“战略感”文案
- 多写具体判断

## 12. Markdown 优先于样式技巧

优先使用稳定的 Markdown 结构：

- 标题
- 段落
- 编号列表
- 项目列表
- 引用块

不要依赖复杂样式来制造层级，因为：

- 导出更容易出问题
- 渲染环境不同会变形
- 过多样式会干扰重点

## 13. 最终自检清单

在生成或修改报告前，至少检查：

- 有没有解释“报告怎么写”，而不是直接说事实
- 有没有新造概念
- 有没有把不该加粗的东西都加粗
- 原问题 / 原答案有没有清楚地和分析结论分开
- 每一节有没有真正的结论句
- 建议是不是能回到事实和验证指标
- 去掉样式以后，这份 Markdown 还好不好读

如果这些问题里有两项以上答不上来，就还不够像人写的报告。

## 14. 人类默会阅读原则

这部分不是文案技巧，而是人类阅读报告时天然会在意的东西。后续不只是 GEO 报告，凡是分析报告、诊断说明、设计说明，都应该默认遵守。

### 14.1 人类首先看的是层级，不是信息总量

读者不会逐字扫描所有内容，而是先靠层级判断：

- 哪一句是结论
- 哪几条是支持这个结论的证据
- 哪些是例子
- 哪些只是补充信息

所以：

- 重点信息必须被放到更高层级
- 结论句必须先于解释句出现
- 例子和原始样本不能和主结论混在一起

如果层级不清楚，哪怕信息很多，读者也会觉得“看完等于没看”。

### 14.2 结论和论据必须紧挨着

人类会天然寻找“这句话为什么成立”的邻近证据。

如果结论和证据被拆得太远，读者就会失去关联感，开始怀疑这是不是在空推导。

因此：

- 结论句下面立刻跟 1-3 条最关键事实
- 原问题、原答案、原引用样本要贴着对应判断出现
- 不要先铺很多背景，再在很后面给结论

判断标准：

- 读者在同一屏内，应该就能看到“结论 + 证据 + 例子”的关联关系

### 14.3 重点必须能一眼扫到

人类对重点非常敏感。

报告里真正需要被扫到的是：

- 关键指标
- 关键结论
- 明确的好消息
- 明确的优化空间

不是所有信息都需要被强化。

所以：

- 关键数字可以加粗
- 少量关键判断可以加粗
- 不要把普通说明句、标签词、过渡词一起加粗
- 不要让“看起来都重要”变成“实际上没有重点”

### 14.4 信息要客观，好坏都要客观

报告不能默认“先找毛病”。

如果品牌客观上做得不错，就应该先明确说：

- 它做得不错
- 好在哪里
- 这个好是由哪些事实支撑的

只有在确实有优化空间时，才继续说：

- 还有哪些地方可以做得更好
- 这些空间是否值得优先投入

禁止这种写法：

- 明明已经排名第一，还默认写成“问题在于……”
- 明明数据不差，还硬用“只有”“还不行”“最大压力来自……”
- 把行业常态误写成品牌缺陷

如果一个“问题”现实里很难避免，或者不构成高优先级经营动作，就不要硬把它写成毛病。

### 14.5 允许主观判断，但主观必须站在客户立场

完全没有主观判断的报告也不好读。

但主观判断必须满足两个条件：

- 站在帮助客户判断轻重缓急的立场
- 有事实依据，不是 AI 自己的推演习惯

也就是说，可以写：

- “当前整体表现不错，更值得优先优化的是官网承接。”
- “和竞品同台并不一定是坏事，因为买车类问题天然会进入比较语境。”

但不要写：

- “问题不在……而在……”
- “真正的问题是……”
- “最大压力来自……”

除非这个判断已经有充分事实支持，而且确实对经营动作有意义。

### 14.6 不要用 AI 视角写人类报告

报告不是在向用户展示模型如何推理，而是在帮助用户更快地做判断。

因此不要：

- 用 AI 自己的分类逻辑取代人类语言
- 把模型默认的“找问题”习惯带进报告
- 用抽象逻辑词替代真实业务表达

应该写成：

- 人类能直接理解的话
- 业务上有意义的话
- 客户看完能知道“我现在做得怎么样、接下来先干什么”的话

### 14.7 样式不是重点，重点是信息结构

人类喜欢好看的排版，但真正决定可读性的不是样式花样，而是：

- 层级
- 邻近关系
- 信息密度
- 重点提取

所以：

- 能用 Markdown 解决，就不要靠复杂样式解决
- 样式服务结构，不要反过来
- 如果去掉样式以后文章就不好读，说明结构本身有问题

### 14.8 低信号的 0 值信息默认不写

不是所有 `0 个 / 0 条 / 0 次` 都值得出现在报告里。

只有当 `0` 本身是一个重要结果时，才值得明确说出来，例如：

- `0 个严重 bug`
- `0 条负面提及`
- `0 次官网引用`

如果 `0` 只是一个低信号的过程计数，就不应该硬写出来，例如：

- `0 个只提竞品`
- `0 个问题最后只提品牌`
- `0 条价格掉出样本`

默认规则：

- `0` 是关键目标达成或关键风险归零：可以写
- `0` 只是无信息增量的子句：直接省略

判断标准：

- 去掉这个 `0` 以后，读者对结论有没有损失？
- 如果没有损失，就不要写

## 15. 后续默认执行规则

从这份原则开始，后续所有报告和分析说明，默认要多做一次这类回溯检查：

1. 有没有先承认客观做得好的地方
2. 有没有把可以优化的地方说成真正有意义的经营动作
3. 结论和论据是不是贴得足够近
4. 重点是不是一眼能扫到
5. 有没有把 AI 的推理习惯误当成人类语言
6. 有没有为了“显得专业”而发明概念

如果这些问题里有任何一项答不上来，就说明这份报告还没有真正符合人类阅读逻辑。
