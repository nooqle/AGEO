## 二、覆盖不足的问题（5 个）

### 1. 情感极性权重太低，负面实体仍可进入内圈

**PRD 现状**（Section 17.1）：

`sentiment_or_risk_score` 权重仅 10%。

**真实问题**：安利的"监管信息"在覆盖度、频次、显式关联等维度全部得高分，负面的情感极性只占 10%，无法阻止它进入内圈。用真实数据代入公式：

```
监管信息的 connection_strength 估算：
  platform_coverage_score = 20/20（4 个平台全覆盖）
  mention_frequency_score = 15/15（54 条回答提到）
  explicit_association_score = 18/20（直销/监管和安利强关联）
  context_relevance_score = 13/15（命中实体词表）
  evidence_quality_score = 8/10
  sentiment_or_risk_score = 0/10（负面语境）
  stability_score = 8/10
  总分 = 82 → 进入内圈（≥75）
```

即使情感得 0 分，总分仍然 82，稳进内圈。10% 权重根本拦不住。

**修复建议**：增加**一票否决规则**——当 `sentiment_or_risk_score < 阈值`（如 < 3/10），无论 `connection_strength` 多高，实体不得进入内圈或中圈，必须进入风险圈或待审阅浮层。这不是权重问题，是分类优先级问题：先判正/负，再判远/近。

### 2. 竞品检测只有关系类型，没有检测方法

**PRD 现状**（Section 17.5）：

关系类型枚举包含 `competes_with`，`Circle Entity State` 有 `competitor_pressure` 字段。

**真实问题**：产品声称发现了 6 个竞品参照，但在图谱和报告中完全看不到。问题不在数据模型（字段都有了），而在**抽取逻辑**——系统怎么知道一个实体是竞品？

PRD 没有定义：
- 竞品实体从哪来？仅靠 EntityLexicon 预定义？还是从 AI 回答文本中识别？
- AI 回答提到"汤臣倍健"时，系统如何判断它是安利的竞品而非无关品牌？
- `competitor_pressure` 怎么计算？从回答中"替代安利"的语境推断？还是从共现频率？

**修复建议**：在 Section 17.5 补充竞品检测规则：

1. EntityLexicon 中标记为 `competitor` 的实体自动进入竞品圈
2. AI 回答中出现"替代""相比之下""不如选 X"等比较语境时，提取竞品关系
3. 竞品关系必须有 evidence span 引用，不能只靠词表标记
4. 每个 `competes_with` 关系应记录竞品在哪些问题/平台上替代了品牌

### 3. 风险圈规则定义了，但风险检测逻辑未定义

**PRD 现状**（Section 17.1）：

风险圈规则：`entity_type = risk`，或风险关系得分 >= 60，或用户标记为风险。

**真实问题**：当前产品中 80 个节点、0 个风险节点。规则写了"entity_type = risk 就进风险圈"，但**谁来给 entity_type 赋值 risk**？这个赋值逻辑完全缺失。

PRD 的抽取流程（17.5）第 4 步说"对实体关系进行分类，生成 relation_type"，其中包含 `risk_of`。但没说：
- 什么条件触发 `risk_of` 分类？是关键词匹配？LLM 判断？还是实体词表预定义？
- 安利的"传销/拉人头"如何被识别为风险而非普通实体？
- `sentiment_or_risk_score` 和 `risk_of` 关系类型的关系是什么？一个管分类，一个管评分，但如何联动？

**修复建议**：在 Section 17.5 补充风险检测规则：

1. EntityLexicon 中标记为 `risk` 的实体自动归入风险圈
2. AI 回答中出现"传销""骗局""智商税"等风险词库命中时，标记 `risk_of` 关系
3. 负面情感 + 高频共现 = 风险信号，而非品牌资产信号
4. 风险实体在图谱上的渲染优先级应高于普通实体（不可折叠、不可隐藏）

### 4. 报告证据选择逻辑完全缺失

**PRD 现状**（Section 17.6）：

"报告正文必须保留关键变化对应的实体、平台、资产引用。"

**真实问题**：当前报告中 8 条证据全部来自同一个问题（Q11）。PRD 没有定义：
- 每个战略词应该引用几条证据？
- 证据应从哪些问题中选取？最相关的？最长的？还是第一个匹配的？
- 是否要求不同问题来源的证据？还是允许所有证据来自同一个问题？

**修复建议**：在 Section 17.6 补充证据选择规则：

1. 每个战略词至少引用 2 个不同问题的证据
2. 证据选择优先级：精准命中 > 跨平台覆盖 > 长文本
3. 不允许同一个问题的回答作为某个战略词的唯一证据来源
4. 证据引用应包含：问题原文、平台、摘录长度、情感倾向标记

### 5. 战略词判断没有分段规则，模板化问题会复发

**PRD 现状**（Section 17.6）：

"变化量很小时生成短报告；变化量大时生成完整报告。" 只定义了报告长度，没定义结论分段。

**真实问题**：12 个战略词稳定度从 54 到 65，但全部得到"可以进入稳定内容资产管理"的相同结论。PRD 的报告生成规则没有要求 LLM 根据评分差异输出不同结论。

**修复建议**：在 Section 17.6 补充战略词结论分段规则：

| 稳定度 | 证据量 | 结论模板 |
|--------|--------|----------|
| ≥ 60 | ≥ 30 | 已站稳：可放大传播，建议进入内容资产管理 |
| 50-59 | 15-29 | 有基础但需补强：建议定向投放 [平台] 的 [场景] 内容 |
| < 50 | < 15 | 尚在萌芽：先补充问题和证据，不建议进入主传播 |
| 任意 | 任意 + 负面情感占多数 | 伴随风险：需要先澄清 [具体风险]，再考虑传播 |

LLM 必须在结论中填入具体的平台、场景、风险名称，不能用泛泛的"可以进入内容资产管理"。

## 三、PRD 新增但仍有缺口的内容

### 6. "并行平台机架"只出现一次，未定义

Section 19 决策第 8 条："画布默认采用'并行平台机架'方案"。这个词在 PRD 全文只出现这一次，没有定义、没有图示、没有交互说明。

从 Workflow Template（Section 11）看，AI Platform Fetch Group 已经是并行的（ChatGPT/DeepSeek/Kimi/Doubao 并行），但画布上怎么表达这种"一组并行节点"？

**修复建议**：在 Section 6（画布交互需求）补充"平台机架"的定义和交互说明，至少包括：
- 视觉上是一组节点还是一个组合节点？
- 用户能否单独运行某个平台？
- 某平台失败时其他平台如何继续？

### 7. "待审阅浮层"在圈层规则中定义了，但在图谱交互中缺失

Section 17.1 新增了"待审阅浮层"作为圈层外的特殊区域，但 Section 8（图谱交互需求）没有任何关于浮层的交互说明：
- 浮层在图谱上怎么渲染？虚线框？半透明？
- 用户如何处理浮层中的实体？接受/拒绝的交互？
- 浮层实体是否影响圈层布局的计算？

### 8. `auto_applied` Patch 的判定条件未定义

Section 17.2 的状态机包含 `proposed -> auto_applied`，但什么 Patch 可以自动应用？PRD 只说了"自动 Patch 只能更新低风险字段；高影响变化进入审阅"，但没定义"低风险字段"和"高影响变化"的边界。

这与待确认问题 Q3 直接相关。如果不定义，实现时会反复争论。

**建议最低定义**：
- 低风险字段：`source_count`、`last_seen_at`、`connection_strength` 的微调（变化 < 10%）
- 高影响变化：圈层迁移、新增实体、新增风险关系、新增竞品关系、别名合并

## 四、PRD 结构问题

### 9. 文档过长，核心决策和补充规格混在一起

PRD 从最初的 ~1000 行增长到 ~1425 行。Section 17（评审阻断项处理）占了近 300 行，内容实际上是独立的技术规格文档（圈层算法、冲突状态机、I/O Contract、抽取流程），不应该嵌在 PRD 里。

**修复建议**：

将 Section 17 拆为独立文档：

| 独立文档 | 来源 | 内容 |
|----------|------|------|
| `spec-circle-allocation-v0.1.md` | 17.1 | 圈层分配规则、评分维度、阈值、迁移规则 |
| `spec-graph-patch-lifecycle-v0.1.md` | 17.2 | Patch 状态机、冲突规则、写入规则 |
| `spec-board-orchestrator-runtime.md` | 17.3 | Board / Orchestrator / Node Runtime 分工 |
| `spec-node-io-contract-v0.1.md` | 17.4 | I/O 类型定义和兼容性规则 |
| `spec-entity-extraction-v0.1.md` | 17.5 | 抽取流程、关系类型、消歧规则 |
| `spec-report-generation-v0.1.md` | 17.6 | 报告生成规则、长度规则、证据选择 |

PRD 本身只保留产品决策和概念定义，技术规格通过引用关联。

### 10. 8 个待确认问题中至少 3 个应该现在就定

| 问题 | 建议答案 | 理由 |
|------|----------|------|
| Q3: 先自动应用还是先审阅？ | **先自动应用低风险，关键项再审阅** | 已有 17.2 状态机支撑；如果全部先审阅，用户会被审阅队列淹没 |
| Q4: 风险圈是否默认折叠？ | **不折叠** | 安利案例证明风险消失是致命问题；风险必须始终可见 |
| Q8: Chat 是否保留全局输入框？ | **保留，但预填上下文** | 冷启动问题已暴露；空白状态用户无处可去，需要全局入口 |

## 五、总结：PRD 修订建议

| 优先级 | 修订项 | 理由 |
|--------|--------|------|
| **P0** | 增加情感一票否决规则（负面实体不进内圈/中圈） | "监管信息"错分的根因 |
| **P0** | 补充竞品检测规则 | 产品声称有竞品但实际为零 |
| **P0** | 补充风险检测规则 | 产品声称有风险但图谱上消失 |
| **P1** | 补充报告证据选择规则 | 8 条证据全来自 Q11 |
| **P1** | 补充战略词结论分段规则 | 12 个词拿到相同结论 |
| **P1** | 定义"并行平台机架"交互 | 只出现一次，无法实现 |
| **P2** | 拆分 Section 17 为独立技术规格 | PRD 过长，核心决策被淹没 |
| **P2** | 定义 auto_applied 判定条件 | 状态机有空缺 |
| **P2** | 补充待审阅浮层交互 | 圈层规则定义了但交互没定义 |
| **P2** | 锁定 3 个待确认问题 | 阻塞实施启动 |

## 六、一句话评审

**PRD v0.2 在产品方向和概念架构上是对的，但它解决的是"做什么"的问题，还没有充分解决"怎么保证做对了"的问题。** 真实产品已经暴露的 5 个核心缺陷（情感极性、风险消失、竞品缺失、证据选择、判断模板化），PRD 只有数据模型层面的覆盖，缺少检测逻辑和判定规则层面的覆盖。补齐这些规则后，PRD 才能从"方向文档"升级为"可实施的产品规格"。
