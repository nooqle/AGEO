# Validation Runtime And Deploy Protocol

日期：2026-04-15  
状态：Active  
适用范围：`D:\AGEO-worktrees\aio-runtime-isolation` 及后续 AGEO feature worktree

## 1. 目标

这份协议解决的不是“怎么多跑几条命令”，而是三个更实际的问题：

1. 避免重复走已经验证失败的路径
2. 让本地修改、运行时验证、上线部署形成同一套闭环
3. 在提交和部署前留下可复用的验证证据，而不是凭记忆判断“应该没问题”

本协议默认约束：

- 不在 `D:\AGEO-main` 直接开发
- 不把未验证的修改直接 merge 到 `main`
- 不在未做健康检查前宣称“已上线”
- 不在已经证明不稳定的路径上反复重试

## 2. 已知坏路径

以下路径已经证明不可靠，后续默认禁止重复使用：

### 2.1 PowerShell 直接写中文源码

风险：

- 中文 UI 文案和 prompt 很容易被写成 `?` / `???`
- `tsc`、`build` 成功不代表源码没有损坏

处理：

- 默认使用 `apply_patch`
- 若必须脚本写文件，使用 Python 显式 UTF-8 I/O
- 写完后必须重新打开文件检查，并扫描 `???`

### 2.2 未核验就宣称部署成功

风险：

- 代码已 push，但服务器还是旧版本
- 服务重启失败，但对外没有第一时间发现

处理：

- deploy 完成的定义必须同时满足：
  - 远端代码 revision 符合预期
  - backend 健康检查通过
  - frontend 健康检查通过
  - 外网入口返回 200

### 2.3 同一 SSH/密码失败路径反复尝试

风险：

- 浪费时间
- 产生错误判断，以为环境不稳定，实际是凭证源不对

处理：

- SSH 或密码第一次失败后，不重复盲试
- 先确认当前凭证来源、主机、端口、用户是否仍然正确
- 只有在凭证源被重新确认后，才继续连接

### 2.4 使用旧 run/旧日志解释当前问题

风险：

- 把已经取消或过期的任务当成 live 任务
- 得到错误根因

处理：

- 每次日志分析必须先确认：
  - `task_id`
  - `task_run_id`
  - `status`
  - 最近 heartbeat / 更新时间
- 不分析未确认 freshness 的旧日志

## 3. 验证层级

### 3.1 Layer 0：工作区和分支验证

必须确认：

- 当前目录是 feature worktree，不是 `D:\AGEO-main`
- 当前分支不是 `main`
- `git status --short --branch` 可解释

失败即停止，不进入后续验证。

### 3.2 Layer 1：源码完整性验证

至少验证：

- 受影响文件能重新打开
- 受影响源码文件不包含新增 `???`
- 没有明显误写的内部术语、泄露 copy、错误中文占位

这一步的目标是排除“源码已经坏了”的情况。

### 3.3 Layer 2：静态正确性验证

按改动类型执行：

- Backend Python 改动：
  - `ruff check`
  - `compileall`
  - 必要时定向 `pytest`
- Frontend 改动：
  - `tsc --noEmit`
  - `npm run lint`

规则：

- 不为了省时间跳过同层校验
- 允许定向测试，但不允许完全不测

### 3.4 Layer 3：运行时验证

目标不是完整 E2E，而是确认运行时没有立刻断裂。

最少确认：

- 环境变量可复用
- 服务能启动
- 关键 runtime 路径仍可达

浏览器/AIO 相关改动时，至少做：

- 真实平台烟测
- takeover 一次完整闭环
- 刷新/重连一次状态恢复

### 3.5 Layer 4：部署验证

只有用户明确要求上线，才进入这一层。

部署完成必须核验：

1. 远端代码 revision 正确
2. backend 本机接口正常
3. frontend 本机接口正常
4. 外网入口正常

推荐最小健康检查：

- `http://127.0.0.1:8000/docs`
- `http://127.0.0.1:3000`
- 外网业务入口首页

### 3.6 Layer 5：验证写回

一次有效验证必须留下这些信息：

- 改了什么
- 跑了什么
- 哪些通过
- 哪些没通过
- 是否已上线
- 还剩什么风险

若没有写回，下一轮大概率会重复犯错。

## 4. 标准执行顺序

每轮修改默认按以下顺序执行：

1. 工作区/分支检查
2. 查看 diff 和受影响文件
3. 源码完整性检查
4. 静态检查
5. 必要的定向测试
6. 运行时烟测
7. 如果上线：部署 + 健康检查
8. 记录结果

不要跳步骤，也不要把“部署”当成“验证”的替代品。

## 5. Repo 内统一入口

统一入口脚本：

- `python scripts/validate_change.py`

它负责：

- 检查当前 worktree/branch
- 枚举当前修改文件
- 对修改过的源码做 `???` 扫描
- 按改动类型执行 backend/frontend 静态检查
- 可选执行定向 `pytest`
- 可选执行 URL 健康检查

它不是完整 E2E 平台，而是每次修改后的最低验证底线。

## 6. 什么时候必须扩展验证

以下改动必须加做更深一层验证，而不只跑静态检查：

- WebSocket / task state / replay / pending_confirmation
- Browser Agent / AIO / takeover / resume
- Artifact 写回
- Orchestrator skill routing
- 部署脚本或线上运行时配置

原则：

- 共享状态层改动，要做刷新/重连验证
- 浏览器接管改动，要做真实平台烟测
- 上线改动，要做 deploy health-check

## 7. 失败处理原则

如果某一层失败，不应直接继续下一层。

必须先回答：

1. 失败发生在哪一层
2. 是代码问题、环境问题，还是验证路径本身有误
3. 这个失败路径是不是以后应该列入“已知坏路径”

如果答案已经明确，就不要重复试同一条坏路径。

## 8. 当前实现边界

本协议当前不覆盖：

- 全量自动化 E2E 编排
- 自动化服务器部署
- 自动化 SSH 凭证管理

这三项后续可以继续建设，但不影响当前先把“每次修改都有一致的验证闭环”落地。
