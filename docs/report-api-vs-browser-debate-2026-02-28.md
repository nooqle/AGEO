# API vs 浏览器采集差异 — 团队讨论报告

> **日期**：2026-02-28
> **参与角色**：产品经理（Marty Cagan）、架构师（Martin Fowler）、QA（James Bach）、UX（Don Norman）
> **议题**：基于实测数据和行业调研，评估 Specta AI 平台的商业价值是否受到根本性冲击

---

## 一、大白话解读测试报告

### 我们做了什么？

我们做了一个很简单的实验：**拿同一个问题，分别用两种方式去问同一个AI**。

- **方式A（API）**：通过程序接口问，就像我们平台后台在做的事情
- **方式B（浏览器）**：打开网页，像普通消费者一样在网页上问

我们在 Kimi 和豆包两个平台上各问了 10 个护肤品相关的问题，然后对比两种方式返回的"推荐品牌"有多少是一样的。

### 结果说明了什么？

**打个比方：假设你派了两个"侦探"去同一家餐厅问"你们招牌菜是什么"。**

- 一个侦探走前门进去（浏览器，消费者视角）
- 一个侦探打电话问（API，程序视角）

结果发现：

| 发现 | 数据 |
|------|------|
| **推荐的菜有一半不一样** | Kimi 48% 重叠，豆包 49% 重叠 |
| **就算推荐了一样的菜，排名顺序也经常不同** | Kimi 的排名一致性接近"扔硬币"，豆包稍好但也不稳定 |
| **完全不可预测** | 有些问题两个侦探带回来的答案一模一样（100%），有些完全不同（0%），而且你事先不知道哪个会一样 |
| **两个餐厅都是这样** | Kimi 和豆包的差异程度几乎一模一样，说明这不是某个平台的特例 |

### 这意味着什么？

**我们平台目前通过"打电话"（API）收集的数据，和消费者"走进店里"（浏览器）看到的推荐，有将近一半是对不上的。**

如果一个品牌方客户说"帮我看看在Kimi上搜护肤品时，我的品牌排第几"，我们通过API拿到的答案，可能和他自己打开Kimi网页看到的答案完全不同。

---

## 二、为什么会这样？（技术原因）

这不是我们的Bug，**这是所有AI平台的结构性特征**：

1. **浏览器版本会联网搜索**：用户在网页上问问题时，AI会先搜索互联网上的最新信息，再综合回答。这叫RAG（检索增强生成）。
2. **API版本通常不搜索或搜索策略不同**：通过API调用时，搜索的范围、关键词策略、引用来源都可能完全不同。
3. **这是行业公认的事实**：
   - OpenAI 社区多次讨论过"API和网页版结果不一致"的问题
   - Perplexity 官方文档明确承认 API 和 UI 输出存在差异
   - 行业监测平台 Otterly.AI 公开警告："有些监测工具声称能大规模追踪话题，但实际上展示的结果是你的客户永远看不到的"

## 三、辩论：商业价值是否被打破？

### 🔴 正方（产品经理 Marty Cagan）：商业价值的根基被动摇了

**核心论点：如果你监测到的不是用户看到的，你卖的就是一个"假仪表盘"。**

#### 论证逻辑

1. **信任链断裂**
   - 我们的产品承诺是：帮品牌方看到"AI怎么推荐你"。
   - 但如果API给出的品牌排名和消费者看到的不一样，品牌方一旦自己去验证（他们一定会），就会发现"你们的报告和我看到的不一样"。
   - 在SaaS产品中，**数据可信度是生命线**。客户只要发现一次不准，整个产品的信任就会崩塌。

2. **E-E-A-T 中的 Trustworthiness（可信度）受到根本性挑战**
   - Google 的 E-E-A-T 框架强调"可信度"是所有其他维度的基础。
   - 如果我们平台的数据来源本身不可信（API ≠ 用户实际看到的），我们就无法帮助品牌方建立其在AI搜索中的可信度。
   - **你无法用一个不准确的工具去帮别人追求准确性。**

3. **"优化"从何谈起？**
   - 品牌方的核心需求是：让更多消费者在AI搜索中看到自己的品牌。
   - 消费者用的是浏览器，不是API。
   - 如果我们监测的是API版本，优化也是针对API版本做的，那最终结果就是：**我们在优化一个消费者永远看不到的版本**。
   - 这就像SEO公司帮你优化了一个只有机器人能访问的页面——客户看不到效果。

4. **商业后果**
   - 品牌方花钱买我们的服务，期望看到"我的品牌在AI搜索中的表现"
   - 如果这个表现是API版本的，和消费者实际看到的有50%的差异
   - **品牌方要么发现了不信你，要么没发现但你帮他们优化的东西没有实际效果**
   - 无论哪种情况，续费都不可能

### 🟢 反方（架构师 Martin Fowler）：商业价值完好，这只是一个工程问题

**核心论点：差异存在，但品牌优化的底层逻辑没有被推翻。通道可以切换。**

#### 论证逻辑

1. **48% 重叠不是 0% —— 核心品牌认知有共性基础**
   - 在我们的测试中，雅诗兰黛、兰蔻、修丽可等头部品牌在API和浏览器中都频繁出现。
   - 差异主要出现在中尾部品牌推荐上。
   - 这说明：**AI对品牌的核心认知（Authority）在两个通道是一致的**，差异来自搜索增强层。
   - 品牌方最关心的是"有没有被提到"和"在头部还是尾部"，这些大趋势在两个通道是相通的。

2. **差异的本质是"信息源"不同，不是"认知"不同**
   - 浏览器版本联网搜索了更多实时信息（小红书、知乎等），所以推荐了更多品牌。
   - API版本主要依赖模型的训练知识，所以偏向知名度更高的品牌。
   - 这不是"AI对品牌的评价不同"，而是"两个版本看到的信息不一样"。
   - **品牌方提升自身内容质量（E-E-A-T中的 Expertise 和 Authoritativeness），无论哪个通道都会受益。**

3. **这是可解决的工程问题**
   - 解决方案很直接：把数据采集从API切换到浏览器自动化。
   - 我们的平台已经有Browser Agent（A6），已经在用Playwright做浏览器采集。
   - 这是几周的工程工作，不是几个月的产品重构。
   - **把管道从API换成Browser，数据就对上了。**

4. **市场验证：竞品都在做同样的事**
   - Otterly.AI、xFunnel.ai 都是做AI搜索品牌监测的，它们的解决方案就是**优先使用UI监测**。
   - 这说明市场需求是真实的，解决方案也是成熟的。
   - 我们不是"发现了一个杀死这个赛道的问题"，我们是"发现了自己的采集方式需要升级"。

5. **AEO 市场在爆发式增长**
   - ChatGPT 周活用户从3亿增长到8亿（不到一年2.6倍）
   - Gartner 预测2026年传统搜索量下降25%
   - 品牌方对"AI搜索可见度"的需求只会越来越大
   - **在一个增量市场里，有技术问题不可怕，可怕的是不在这个市场里。**

6. **架构迁移方案**
   - 当前：`API_PLATFORMS = ["doubao", "hunyuan", "kimi"]`，DeepSeek已经是Browser采集
   - 目标：全部迁移到 Browser-first，API 作为降级备选
   - 改动范围：`nodes_a4.py` 中的采集逻辑 + 各平台 Handler
   - 已有基础设施：Browser Agent、Playwright集成、Handler抽象层
   - 预估工作量：2-3周可完成核心平台迁移

### 🟡 QA 审查（James Bach）：数据能支撑多大的结论？

#### 方法论问题

1. **样本量偏小**
   - 10个问题 × 2个平台 = 20个对比样本
   - 其中有效的只有17个（3个浏览器失败）
   - 统计学上，这只能说明"存在明显差异"，但**差异的精确程度（48%还是55%还是40%）不能当作定论**
   - 建议：至少需要50-100个问题、多次重复测试、覆盖多个行业领域

2. **品牌提取可能有遗漏**
   - 我们用60个品牌的词典做正则匹配
   - AI可能推荐了词典里没有的品牌（如"百花萃"、"The Feelist"等小众品牌）
   - 这可能导致我们**低估了差异**（因为漏掉的品牌更多在一侧出现）

3. **AI回答的固有随机性**
   - AI每次回答都有随机性（temperature参数）
   - 我们只问了一次，没有重复验证
   - 可能有些"差异"其实是**同一个通道自身的波动**，不是API vs 浏览器的差异
   - 建议：同一个问题通过同一个通道问3次，先测量"自身一致性"

4. **失败样本的影响**
   - 豆包Q9/Q10浏览器创建了`local_`会话（离线），Kimi Q7超时
   - 这些被当作"差异"计入了统计，但实际上是采集失败
   - 排除这些后，有效数据的差异可能更大或更小

#### QA 结论

**数据足以证明"API和浏览器存在显著差异"这个方向性结论，但不足以精确量化差异程度。需要更大规模、更严格的测试来确认。**

---

### 🔵 UX 视角（Don Norman）：品牌方客户会怎么想？

#### 场景分析

1. **验证场景**
   - 品牌方市场总监收到我们的报告："您的品牌在Kimi上排名第3"
   - 她打开Kimi网页自己问了一下，发现自己的品牌根本没出现
   - **她的第一反应不是"哦，可能是API和浏览器的差异"，而是"这个工具不准"**
   - 一次验证失败 = 信任归零

2. **但是，品牌方也知道AI有随机性**
   - 越来越多的品牌方已经意识到AI搜索不像百度搜索那样有固定排名
   - 他们的期望可能不是"精确到第几名"，而是"我在不在被推荐的名单里"
   - **如果我们的定位是"趋势洞察"而非"精确排名"，容错空间就大得多**

3. **价值定位的关键转变**
   - ❌ 错误定位："告诉你精确排名第几"
   - ✅ 正确定位："告诉你在AI搜索生态中，你的品牌被提及的频率、语境、竞品对比趋势"
   - 趋势层面，API和浏览器的数据是**方向一致**的：被频繁推荐的品牌在两个通道都被推荐

4. **信任修复策略**
   - 透明披露采集方式（"本报告基于浏览器实际采集"）
   - 提供"多次采样"数据，展示波动范围而非单一数值
   - 用"品牌出现率"（10次问答中出现了几次）替代"单次排名"

## 四、综合结论

### 辩论裁决：商业价值**没有被打破，但地基需要加固**

| 维度 | 判断 |
|------|------|
| 商业逻辑 | ✅ 成立 — 品牌在AI搜索中的可见度优化是真实需求，市场在爆发 |
| 数据通道 | ⚠️ 需切换 — API采集的数据和用户实际看到的有~50%差异，必须迁移到Browser |
| 产品定位 | ⚠️ 需调整 — 从"精确排名"转向"趋势洞察 + 出现率"，降低对单次精确度的依赖 |
| 技术可行性 | ✅ 可解决 — 已有Browser Agent基础设施，2-3周可完成迁移 |
| 市场验证 | ✅ 有竞品 — Otterly.AI、xFunnel.ai等已在做类似业务，且都采用UI优先策略 |

### 为什么说没被打破？

**因为品牌方的核心痛点——"我在AI搜索中被推荐了吗？怎么才能更多被推荐？"——这个问题依然存在，而且随着AI搜索的爆发，需求只会更大。**

我们发现的差异，本质上说明的是：**用错误的工具（API）去测量正确的东西（用户实际看到的推荐），需要换一个正确的工具（浏览器采集）。**

这就像一个体检中心，之前用的血压计有偏差。发现了偏差不意味着"体检"这门生意没有价值，而是意味着需要换一个更准的血压计。

### 为什么说地基需要加固？

1. **如果不切换到Browser采集**，我们就是那个"用偏差血压计做体检"的机构——早晚会被发现
2. **如果不调整产品定位**，客户的期望管理会出问题——没有任何AI监测工具能保证"你每次去问都是同一个排名"
3. **如果不增加采样次数**，单次快照的波动太大，报告的可信度不够

## 五、行动方向与推进计划

### P0：Browser-First 采集迁移（1-2周）

| 项目 | 内容 |
|------|------|
| 目标 | 所有核心平台从API采集切换到Browser采集 |
| 范围 | Kimi、豆包 → Browser-first；API作为降级/对照 |
| 技术方案 | 基于现有 Browser Agent + Playwright Handler 架构 |
| 验收标准 | 新采集数据与用户浏览器手动验证的一致性 > 85% |

### P1：产品定位调整（同步进行）

| 项目 | 内容 |
|------|------|
| 核心指标重定义 | 从"排名"转向"出现率"（10次问答中品牌出现了几次） |
| 多次采样机制 | 同一问题采集3-5次，提供置信区间而非单一值 |
| 报告透明度 | 明确标注采集方式、采样次数、数据时间窗口 |
| BWVS指标升级 | 融合"出现频率 × 位置权重 × 语境正负面"的综合分数 |

### P2：数据可信度验证（第3-4周）

| 项目 | 内容 |
|------|------|
| 扩大测试规模 | 50+问题 × 4平台 × 3次重复 = 600+数据点 |
| 跨行业覆盖 | 护肤品、3C数码、餐饮、金融等多领域 |
| 自身一致性测量 | 同通道多次采样的波动基线 |
| 竞品对标 | 对比 Otterly.AI / xFunnel 的方法论和数据质量 |

### P3：差异化竞争壁垒（中期）

基于 E-E-A-T 原则，我们的平台不仅要**监测**品牌的AI可见度，更要**帮助品牌提升**：

- **Experience**：分析品牌内容是否展现了真实的用户体验
- **Expertise**：评估品牌在AI回答中被引用时的专业度表现
- **Authoritativeness**：追踪品牌在多个AI平台上的被引用一致性
- **Trustworthiness**：监测品牌推荐的语境（正面/中性/负面）

**这才是我们和纯监测工具的根本区别——不只是"告诉你现在排第几"，而是"告诉你怎么做才能被更多AI推荐"。**
