## 第一部分：战略层

### 1.1 一句话定位

**LLM 编排的透明化基础设施**——智能系统的每一步编排决策都有形状、可审、可改。

市面上的 Agent 产品把脑内活动藏起来（因为乱、因为不稳）。我们反过来：**把脑内活动变成产品的核心界面**。

### 1.2 与 Dify 的本质差异（Inversion）

| | Dify / n8n / Coze | Specta 新系统 |
|---|---|---|
| 图的作者 | 人搭 Flow | LLM 生成 Flow |
| LLM 的角色 | 在节点里填空 | 编排的主体 |
| 人的角色 | 开发者 | 编排的审计者 |
| 产品性质 | 开发工具 | 智能的显影液 |

同一张画布，两种完全相反的智能-人关系。这是护城河的来源。

### 1.3 为什么要抛弃 Dashboard+Chat

Chat 编排的根本缺陷：**Orchestrator 的计划是隐式的**。它脑子里有 plan，streaming 出几行文字，然后就开始执行。用户面对一个假装开放的输入框，背后跑着既看不见也改不动的固定路径。inline_confirmation 卡片缓解过这个问题（先呈现计划再确认），但文字卡片是一次性的、平面的，确认完就消失。

被抛弃的只是 Dashboard+Chat 这套**外壳**。引擎、工具、经验全部保留（见 2.6 包袱映射表）。

### 1.4 三个核心命题

**拓扑即计划（Topology as Plan）**
Orchestrator 的编排结果物化为持久、可编辑的图。一张图承载四个生命周期：

- **设计时**：用户看到完整依赖结构，知道"这个系统会干什么"
- **确认时**：Orchestrator 生成的编排以图呈现，用户确认的是一张图
- **运行时**：图变成状态面板（Phase 2 运行态映射已验证）
- **事后**：图是资产——跑过的路径、产出的数据挂在节点上，可回溯可复用

**约束即节点（Constraint as Node）**
自然语言约束的根本问题是不可见：用户在 chat 里说"这次别跑 Kimi"，这句话没有形状——进了 prompt，管不管用、怎么管的，无从验证。用户在画布上断开 Kimi 的连线、加一个自定义节点，约束是有形状的：看得见、改得掉、下次还在。

自然语言擅长表达意图，图擅长承载约束。两者各司其位。

**Chat 即编译器（Chat as Compiler）**
Chat 在新系统里的最终位置是编排的编译器：

```
自然语言 → Orchestrator → 拓扑 diff → 画布呈现 → 用户确认 → 执行
```

LLM 的产出从"直接执行"变成"生成图"。用户说"帮我针对竞争对手做一次舆情分析"，Orchestrator 不直接开跑，而是往画布里放下新节点、连好线，用户看到"它打算这么干"，确认或调整后再执行。Chat 的便利性（表达意图零成本）保留，黑盒性（不知道要干嘛）消失。

### 1.5 智能复利

系统的长期目标：通过"拆解 → 实现 → 反馈 → 校准 → 更复杂任务的拆解"循环，Orchestrator 在约束下持续变聪明——更懂品牌、更懂客户、执行更稳定。

复利不会自动发生，它有三个载体：

| 载体 | 机制 | 效果 |
|---|---|---|
| **拓扑复利** | 成功编排路径沉淀为模板，同类意图从模板出发微调 | 拆解稳定性递增，执行路径收敛 |
| **资产复利** | 词库/问题集/报告/校准实体逐轮增厚 | 每次运行起点更高；积累过程客户可见（续费理由） |
| **校准复利** | 用户干预（删实体/断连线/否决编排）成为修正信号 | Orchestrator 对该客户的理解被持续校准 |

**透明系统的隐藏优势**：黑盒 Agent 的用户反馈是模糊的（"结果不好"），系统不知道该改哪。我们的用户改的是**具体的图**——删的是某个节点、断的是某条边、改的是某个配置项。反馈天然带结构、带位置，校准有精确落点。可视化不仅给人看，也给系统自己看。

**有边界的复利才是资产**：系统自我提升的自由度被拓扑约束、工具白名单、审批闸口框住。客户知道它再怎么进化也出不了这个圈。无边界的复利是风险。

### 1.6 To B 论证：可问责的 AI

企业买的从来不是聪明的 AI，是可问责的 AI。可视化提供三层问责：

- **事前可审**：plan 有形状，批准了才跑
- **事中可控**：运行状态实时可见，可中断
- **事后可查**：执行路径回放，资产沉淀

另外两个差异化支点：

- **稳定性的可度量**：同一意图多次拆解，Orchestrator 收敛到相似拓扑——拓扑相似度本身成为稳定性指标，黑盒系统连定义都定义不了这个指标
- **记忆可见 = 合规刚需**：词库、历史、偏好全部物化为可见、可编辑、可删除的对象（见 2.5），满足数据可审计、可擦除要求

### 1.7 平台化：一套基建，多个垂直产品

框架按编译器三段式设计，保证可快速改造出数据分析平台、代码生成平台等新产品：

| 层 | 职责 | 领域相关性 |
|---|---|---|
| 前端：意图解析 | 领域词表、意图模板、拆解 prompt | 每领域一套 |
| 中端：拓扑编排引擎 | DAG 理解、节点调度、运行态投影 | **通用，一套引擎** |
| 后端：Tool 集 | 采集器 / 数据连接器 / 代码执行器 | 每领域一组 |

amwaychina 验证的恰恰是中端引擎和前后端接口——最难也最通用的部分。做数据分析平台 = 写新的前端词表 + 一组数据 Tool，引擎和画布原样端走。

**命根子原则**：节点注册表契约里只允许出现领域无关的概念（inputs/outputs/config/执行能力），任何安利味的字段不得漏进契约层。

### 1.8 演进路径

```
3a（已完成）画布 = 展示层，拓扑仅视觉
3b-1  节点注册表 + 拓扑感知编排：用户画图 → Orchestrator 按图执行
3b-2  计划可视化：chat 发起的任务，Orchestrator 的规划投影到画布
3c    chat-to-topology：自然语言 → 生成/修改图 → 确认 → 执行
```

3b-2 几乎是 3b-1 的副产品：Orchestrator 理解拓扑语言后，规划 chat 任务时顺手把规划翻译成图投影出来。到 3c，chat 与画布真正统一——chat 是生成图的方式之一，画布是编排的唯一载体。

## 第二部分：架构层

### 2.1 三层模型

```
Intent 层：客户意图（"安利在外部 AI 眼里什么样"）
    ↓ Orchestrator 拆解
Plan 层：拓扑（画布上可见、可改的图）
    ↓ 调用
Tool 层：节点注册表（内置节点 / 外部 AIO 服务器 / 未来的自创代码节点）
```

换客户/换领域时：Intent 层换 prompt，Tool 层加注册，Plan 层由 Orchestrator 自动生成——**引擎不动**。每个行业意图沉淀为一个模板（预置拓扑 + 节点组合），amwaychina 是"品牌可见度诊断"模板的第一个客户。

### 2.2 节点注册表契约（平台级）

每个节点自描述，Orchestrator 编排时读两样东西：节点注册表（有哪些节点、各自吃什么吐什么）+ 用户拓扑（这次的依赖约束）。

```ts
interface NodeContract {
  id: string;                        // 'fetch' | 'extract' | 'analysis' | ...
  kind: 'asset' | 'executor' | 'producer';
  inputs: PortSpec[];                // [{ type: 'questions', required: true }]
  outputs: PortSpec[];               // [{ type: 'answers' }]
  configSchema: Record<string, ConfigField>;  // 配置面板与 LLM 共读的 schema
  executor: ExecutorRef;             // 后端执行单元引用
  description: string;               // 给 Orchestrator 读的能力说明（进 prompt）
}
```

契约设计纪律：

1. **领域无关**：契约层只有 inputs/outputs/config/executor，业务语义（品牌、圈层）留在具体节点实现与 prompt 里
2. **LLM 可读**：description 与 configSchema 直接构成 Orchestrator 的 tool 描述，注册表即工具书
3. **双端同源**：画布渲染、配置面板、Orchestrator 编排读同一份注册表，无第二处事实

### 2.3 拓扑感知编排

核心原则：**图决定"可以怎么走"，LLM 决定"实际怎么走"。**

Orchestrator 在拓扑约束内保留动态性：

- 某平台失败 → 它决定重试还是跳过
- 中间结果不够 → 它决定回到上游节点补数据
- 用户加了自定义节点 → 它按输入输出契约把新节点编进执行路径
- 无拓扑约束（chat 自由任务）→ 它自己生成拓扑再执行（3c 闭环）

编排 prompt 的两种模式：

| 模式 | 输入 | Orchestrator 职责 |
|---|---|---|
| 约束模式（画布发起） | 用户拓扑 + 节点注册表 | 按图调度，处理运行时分支 |
| 自由模式（chat 发起，3c） | 意图 + 节点注册表 | 生成拓扑 → 呈现 → 确认后按图调度 |

两种模式共用一套引擎与注册表，chat 流程与画布流程由此统一。

### 2.4 A1–A5 迁移方案

老 agent 不重构、不废弃，**降级为可编排的普通节点**：

| 旧节点 | 新形态 | 说明 |
|---|---|---|
| A4 采集 | 直接节点化 | 最坚实的 Tool 层资产（反爬/handler/parser/熔断），不动 |
| A5 分析 | 直接节点化 | 兼作"数据分析"自定义节点的能力底座 |
| A1 品牌分析 + A2 人群 | 词库生产器节点 | 不再必经；用户要扩词库时才编进图 |
| A3 问题生成 | 问题集生产节点 | 与"上传问题集"平级——同一资产节点的两种来源 |

A1/A2/A3 的产出物（词库、问题集）在新模型里从"每次运行现算"变成"可沉淀复用的资产"，生产器节点是资产的工厂。老 chat 场景下 Orchestrator 仍可按老顺序调它们——顺序在它脑子里，不在代码里。

### 2.5 记忆与资产的物化

amwaychina 已验证：词库、问题集、历史报告是画布上的资产节点——它们本质上就是**记忆的物化**。向外扩展：

| 记忆类型 | 物化形态 | 状态 |
|---|---|---|
| 领域知识 | 词库/问题集资产节点 | 已有 |
| 运行产出 | 报告/圈层图资产 | 已有 |
| 用户偏好 | 节点 config + 拓扑模板 | 3b 成型 |
| 历史编排 | 拓扑模板库（拓扑复利的载体） | 3c 后 |
| 运行教训 | 节点级 annotation（"上次这个平台失败了"） | 后续 |

全部可见、可编辑、可删除——合规刚需与产品差异化合一。

### 2.6 包袱映射表（老系统资产 → 新系统位置）

| 老资产 | 新系统里的位置 |
|---|---|
| Orchestrator + Function Calling | 大脑，原样保留，增加拓扑感知 |
| TPAOR 框架 | 节点内部执行的思考结构 |
| A4 采集体系 | Tool 层核心资产，直接节点化 |
| A5 分析 | 分析 Tool + 自定义分析节点底座 |
| A1/A2/A3 | 资产生产器节点 |
| inline_confirmation | 图确认模式的哲学前身 |
| WebSocket 运行事件 | 画布运行态数据管道（Phase 2 已复用） |
| prompts/ 全部提示词 | 节点级 prompt 资产库 |

### 2.7 受控自扩展（自创代码节点）

Orchestrator 缺工具时可提议自写代码节点——与可视化哲学自洽：**生成的代码呈现在画布上，人审过了才跑**。To B 两道闸：

1. 沙箱执行（隔离资源与数据访问）
2. 入注册表需管理员审批

价值主张：别的平台缺工具要提工单等排期，我们的系统现场长出工具，还带着完整审计链。归入 3c 之后的路线图，本期不做。

## 第三部分：实施层（3b 拆分）

### 3b-1 节点注册表 + 拓扑感知编排（核心期）

| # | 任务 | 说明 |
|---|---|---|
| 1 | 节点契约定义 + 注册表骨架 | 平台级契约（2.2），先注册 amwaychina 现有节点 |
| 2 | A4/A5 输入输出显式化 | 当前隐式读写 state 固定字段 → 按契约显式 IO（**最硬的骨头**） |
| 3 | Orchestrator 拓扑感知 prompt | 约束模式：读拓扑 + 注册表 → 按图调度 |
| 4 | 拓扑存储上后端 | 新表 flow_topology（entity_id/nodes/edges/version），localStorage 迁移 |
| 5 | 自定义节点（分析/内容）真执行 | 分析节点接 LLM 解读（自定义 prompt 二级解读接口）；内容创作节点接词库+分析产出草稿 |
| 6 | 局部运行 | 只跑拓扑的某个分支（如只重跑内容创作节点） |

验收：用户在 amwaychina 画布断开某平台连线后运行，Orchestrator 实际跳过该平台；新增数据分析节点连入拓扑后，运行结果包含该节点的 LLM 解读产出。

### 3b-2 计划可视化

| # | 任务 | 说明 |
|---|---|---|
| 1 | Orchestrator 规划 → 拓扑投影 | chat 发起任务的执行计划实时呈现在画布 |
| 2 | 意图相似度 → 模板推荐 | 命中已有拓扑模板时预填画布 |

### 3c chat-to-topology

| # | 任务 | 说明 |
|---|---|---|
| 1 | 画布内聊天输入 | 自然语言 → 拓扑 diff（新增/修改节点连线） |
| 2 | 图确认流 | 拓扑 diff 呈现 → 用户确认/调整 → 执行（inline_confirmation 的图化升级） |
| 3 | 拓扑模板库 | 成功编排沉淀为模板，复利启动 |

### 风险与对策

| 风险 | 对策 |
|---|---|
| A4/A5 IO 显式化动到稳定采集链路 | 契约适配层包裹，执行内核不动；全量回归 53 个 parser 测试 + E2E |
| Orchestrator 按图调度的可靠性 | 拓扑校验前置（DAG/类型匹配在保存时拦截），LLM 只处理运行时分支 |
| 3b-1 范围蔓延成平台大重构 | 注册表按平台级设计，节点只迁 amwaychina 需要的；A1/A2/A3 通用化等 chat 主流程迁移时再做 |
