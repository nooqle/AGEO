## 项目架构审查报告

### 一、当前架构概览
项目采用 **Mini-Agent 架构**，核心组件：
- **Orchestrator Agent** (`orchestrator.py`) - 主控 Agent，使用 ReAct 模式
- **General ReAct Agent v2** (`general_react_v2.py`) - LLM 驱动的编排
- **LLM Orchestration Engine** (`llm_orchestrator.py`) - 决策引擎
- **Agent Registry** (`registry.py`) - Agent 能力注册
- **Tool Registry** (`tools/registry.py`) - 工具注册

### 二、发现的架构问题

#### 1. **重复/冗余的 API 端点** (高优先级)
- `app/api/chat.py` 和 `app/api/minimax_chat.py` 功能重叠
  - 两者都提供 `/stream` 和 `/chat` 端点
  - 都使用 MiniMax 模型
  - 但实现方式不同（一个用 Orchestrator，一个直接调用模型）
- **影响**: 维护困难，客户端不知道该用哪个

#### 2. **两套并行架构** (高优先级)
- **旧架构**: `general_react.py` (硬编码流程)
- **新架构**: `general_react_v2.py` + `llm_orchestrator.py` + `orchestrator.py`
- **问题**: 代码分散，职责不清，存在多个入口点

#### 3. **重复的 Registry 模式** (中优先级)
- `app/agents/registry.py` - AgentRegistry
- `app/tools/registry.py` - ToolRegistry
- 两者都是单例模式，功能相似但管理不同概念
- **影响**: 概念混淆，Agent 和 Tool 边界不清

#### 4. **未使用的代码文件** (高优先级)
- `general_react.py` - 旧版本，被 v2 替代
- `step_by_step_orchestrator` (只有 .pyc，无 .py)
- `services/agent_orchestrator.py` - 可能与新架构重复

#### 5. **API Router 混乱** (中优先级)
- `router.py` 同时包含 v1 和直接路由
- `minimax_chat` 和 `chat` 都挂载到 `/api/v1` 下
- 路径设计不一致

#### 6. **Schema 分散** (低优先级)
- `app/schemas/orchestration.py` - 新架构
- `app/schemas/pipeline.py` - 旧架构
- 存在重复或类似的类型定义

### 三、优化方案

#### Phase 1: 清理重复代码
1. **删除 `general_react.py`** (旧版本)
   - 保留 `general_react_v2.py` 作为唯一主控 Agent
   
2. **合并 API 端点**
   - 删除 `minimax_chat.py` 或将其功能合并到 `chat.py`
   - 统一使用 Orchestrator 模式
   
3. **清理未使用的 services**
   - 检查 `services/agent_orchestrator.py` 是否被使用
   - 如与新架构重复，删除或合并

#### Phase 2: 统一架构概念
1. **明确 Agent vs Tool 边界**
   - Agent: 有状态、有复杂逻辑的专业模块 (A1-A5)
   - Tool: 无状态、单一功能的可调用单元
   - 考虑合并 Registry 或明确区分使用场景

2. **统一事件流**
   - 目前存在 `AgentEvent` 和 SSE 事件两种格式
   - 统一为一种事件格式，减少转换成本

#### Phase 3: 代码组织优化
1. **API 路由重构**
   - 统一前缀：`/api/v1/chat`
   - 移除重复的 minimax_chat 路由

2. **Schema 合并**
   - 将 orchestration 相关 schema 合并
   - 删除废弃的 pipeline schema

### 四、实施建议
1. **先清理，后重构** - 删除未使用文件风险最低
2. **保留新架构** - `general_react_v2` + `llm_orchestrator` 设计更优
3. **逐步迁移** - 先确保新架构稳定，再删除旧代码
